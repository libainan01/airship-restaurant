# 飞艇餐厅 R5 订单厨房阶段实现记录 v0.1

## R5-01：Order 模块

- 新增独立 `OrderModule`，统一持有待提交点单、正式订单、订单项、单份餐点、餐桌绑定、顾客组绑定、食材预定引用和结算引用。
- 桌边完成选菜时只创建待提交点单，不创建正式订单，也不广播厨房通知；服务员在订单传递点提交后，才原子创建唯一正式订单并广播 `order.created` 与 `order.kitchen-notified`。
- 一张餐桌在待提交或存在未结正式订单期间不能创建第二份待提交点单；同一待提交点单重复提交到同一正式订单时返回幂等成功，不会重复建单或重复通知厨房。
- 正式订单只使用已提交、履约中、待结账和已结算四种汇总状态，并完全由单份餐点状态和结算事实派生，不开放外部直接覆盖状态的 API。
- 每个点餐份数生成一个稳定餐点实例，独立经历待制作、制作中、待取餐、运输中、已上桌和已食用六个顺序状态；跨级推进会被拒绝。
- 餐点可保存临时阻塞原因。阻塞期间拒绝推进，条件恢复后可继续履约；正式订单不提供取消、失败或超时终态。
- 正式订单创建时保存基础单价、经营调整和成交单价快照，并同时锁定专注模式加成比例；后续菜单或经营效果变化不追溯已有订单。
- 每份餐点进入已上桌状态时锁定该次送餐产生的小费，结账时从餐点快照聚合，不允许 UI 临时传入或覆盖小费。
- 全部餐点已食用后自动进入待结账。结账根据订单价格快照计算菜品销售额，根据订单创建快照计算专注加成，并把销售、小费和专注加成作为独立财务流水。
- 订单结账与 `FinanceModule` 使用同一事务：财务批次写入或订单状态切换任一失败时整体回滚；结算键固定为订单 ID，重复结账不会产生第二个批次或重复增加余额。
- 创建、餐点状态变化、阻塞、恢复、进入待结账和完成结算均发布唯一领域事件；同一餐点多次阻塞恢复不会因事件 ID 冲突而丢失广播。
- 只读模型提供待提交点单、未结订单、最近已结订单和当前未结餐点状态数量，历史订单不会污染当前经营进度。
- 版本化状态保存订单业务事实、价格与收益快照、阻塞原因及外部食材预定引用；构造恢复不会重放历史事件，也不保存临时 Task 实例。

## R5-02：整桌食材预定事务

- Order 通过只读食谱目录端口读取简化游戏食谱，把同桌所有订单行和份数聚合成整桌基础食材需求；详细现实食谱和调味品不参与业务库存计算。
- 提供无副作用的食材可用性检查结果，明确返回未知食谱、缺少的食材与数量、具体堆叠位置分配和符合条件的上行在途单件 ID，供后续顾客选菜流程过滤不可点菜品。
- 食材来源按配置的稳定顺序分配；Demo 顺序固定为飞艇交换站食材仓、正在上行的在途食材、地面交换站库存。尚未送达的采购地点不进入来源配置，因此不计入可点库存。
- 创建待提交点单时不接受外部伪造的预定结果，而是在 Order 与 Inventory 的同一事务中重新读取最新可用量、创建唯一整桌预定并写入待提交点单。
- 同桌多道菜和同菜多份只建立一个整桌库存预定；任一食材不足时整个待提交点单失败，不保留部分库存绑定或已处理操作 ID。
- 多桌在预览阶段都可能看到菜品可点，但正式创建时必须重新校验；先成功的桌绑定具体单位，后续桌收到食材不足结果并按最新库存重新选菜，不会发生超卖。
- 库存预定保存具体位置与数量，不会因为其他位置后来补货而自动换绑；正式订单只继承待提交点单的预定 ID，不再次预定或重复扣减。
- Inventory 预定请求增加上行在途堆叠单件绑定。预定、释放、运输到站与最终消耗继续复用同一库存账本，货物的 reservationId 不由订单旁路保存。
- 订单领域事件与库存预定事件在事务提交后一起广播；库存拒绝、状态校验或事件校验任一失败时，Order 与 Inventory 同时回滚。
## R5-03：RecipeExecution DAG

- 新增独立 `RecipeExecutionModule`。正式订单中的每一份餐点分别创建一个执行实例，不同份数、订单或餐点之间不共享步骤状态。
- 执行实例完整保存创建时的食谱 ID、显式版本、基础食材、步骤定义、设备能力需求、在场规则、基础时长、步骤输入输出和质量权重快照；后续内容调整只影响新实例。
- 步骤使用锁定、可执行、执行中、阻塞和已完成五种状态。没有前置依赖的根步骤在实例创建时同时开放，并广播独立的 `recipe.step-ready` 事件。
- 线性步骤只在直接前置完成后开放；汇合步骤逐项检查全部前置状态，任何一个分支未完成时都保持锁定。
- 可执行步骤可以记录阻塞原因并从 Task 投影中移除；条件恢复后重新进入可执行状态并重新广播，不取消订单、执行实例或食材预定。
- 每次步骤开始、阻塞、恢复、完成以及整份食谱执行完成均发布唯一领域事件；步骤时间使用单调校验，禁止完成时间早于开始时间。
- 每份餐点和步骤使用确定性的稳定 ID；Task 键使用稳定短哈希，避免较长订单与内容 ID 拼接后超过通用任务 ID 上限，同时保留原始 mealId 与 definitionStepId 业务引用。
- `createTaskSourceSnapshot()` 只把当前可执行步骤投影为厨师等待任务，锁定、阻塞、执行中和已完成步骤不进入等待队列；Task 持久化仍不保存临时队列。
- 存档保存执行实例和步骤事实；读档后不会重放历史事件，并可从当前步骤状态重建完全相同的等待任务集合。
- 静态食谱目录在装配阶段拒绝重复步骤、未知依赖、自依赖、循环、多最终出口、基础食材重复计算和最终输出不一致。
- ContentRegistry 同步增加构建期 DAG 校验，并为每份游戏食谱增加显式 `version`；内容生成工具已重新生成类型安全数据。

## R5-04：厨房设备、工作位与备餐缓存

- 新增独立 `KitchenFacilityModule`，只管理步骤对厨房工作位、交互点和备餐缓存槽位的预订、运行占用与释放；建筑实例、二维坐标和世界几何仍由 SceneLayout 持有。
- 新增 `KitchenFacilityAdapter`，按建筑定义、等级和当前实例投影稳定工作位与缓存槽位。业务状态只保存建筑、工作位、缓存槽位和交互点 ID，不缓存坐标；设备移动后继续引用同一资源，由 Movement 根据 SceneLayout 最新修订重新寻路。
- 步骤按所需能力集合动态选择当前可用工作位，不判断煎炒灶、蒸煮灶等具体建筑类型；单个工作位可提供多项能力，同一工作位和交互点同时只允许一个步骤占用。
- 工作位、备餐缓存和角色移动交互点在同一事务中预订。角色不存在、交互点无容量或无法寻路时全部回滚，不留下已占工作位、缓存槽位或已处理操作 ID。
- 无匹配能力、工作位全忙和备餐缓存已满分别返回稳定拒绝码，调用方可让 RecipeExecution 步骤进入等待；失败发生在占用和食材消耗之前。
- 在场步骤启动后持续保留厨师、工作位和交互点；无人值守步骤启动后立即释放厨师和交互点，但工作位继续占用到完成。已经运行的步骤不能通过预订释放接口中断。
- 预订到达失败或超时可统一释放工作位、交互点与尚未产出的缓存预订。完成中间步骤时工作位释放，缓存槽位从预订转为占用，并一直保留到同一执行实例中获准的后续步骤取走。
- 缓存声明保存所属食谱执行实例、来源步骤和允许消费的后续步骤；当前只代表场景容量与所有权，具体半成品对象在 R5-06 建立。
- 忙碌设备仍可移动和更换纯外观；拆除、停用、收纳或升级掉正在使用的工作位、交互点、能力和缓存槽位会被建筑迁移约束拒绝。
- 工作位占用、缓存预订/占用、等待超时和操作幂等记录全部进入版本化状态；读档恢复不重放事件，并保留原工作位、缓存及移动目标关联。
- 建筑内容目录补齐 `building.baking_station` 与 `capability.baking`，基础切配、煎炒、蒸煮、烘烤、装盘能力均可使用同一通用占用结构。

## R5-05：厨师任务、执行计时与质量快照

- 新增 `KitchenStepExecutionModule` 作为应用层协调器，把 RecipeExecution、KitchenFacility、Task、Movement、Inventory、Order 与 Character 串成单一步骤生命周期，不把调度职责塞回任一领域模块。
- 可执行步骤领取时读取通用 Task 候选资格，按步骤能力预订工作位、交互点和必要的备餐缓存；资源不足时 Task 保持等待，不提前绑定厨师或消耗食材。
- 整桌库存预定新增按步骤部分消耗接口。并行步骤可从同一个整桌预定依次消耗各自基础食材；未到达厨房存储的在途预定不会被视为可消耗，启动失败后工作位、移动预约、厨师分配和 Task 一起退回等待。
- 步骤真正启动时读取 Character 中实际厨师的烹饪等级，并固化烹饪等级、速度倍率、有效时长、质量权重和加权质量快照；之后升级技能不会追溯已经启动的步骤。
- 默认性能策略为可替换的 `LinearCookingPerformancePolicy`：一级为基础速度，之后每级暂按 1% 速度增益计算有效时长；该参数集中在策略中，可在数值平衡阶段替换，不进入设备定义。
- 设备只参与能力与工作位可用性，不进入速度和质量计算；移动设备、改变外观或后续提升工作位数量均不会改变已启动步骤的厨师快照。
- 在场步骤启动后把 Task 锁为不可中断，并且只有负责厨师仍位于原工作位当前交互点时才推进；设备移动触发重新寻路期间步骤暂停，厨师重新到达后从原进度继续。
- 无人值守步骤完成启动操作后立即结束角色 Task 并释放移动交互点，设备工作位继续自动计时；厨师可以马上领取另一项工作，后续属性变化不影响该自动步骤。
- 预订超时由协调器统一清理，确保工作位、缓存预订、Movement 计划、厨师分配和 Task 同时释放，不产生跨模块残留。
- DAG 前置步骤完成后，协调器自动把新开放步骤同步为等待 Task；首次装配和读档恢复也提供显式同步入口，不会出现 RecipeExecution 已开放但 Task 队列没有任务的断层。
- 版本化状态保存负责厨师、Task 请求、食材预定引用、已消费输入、在场规则、有效时长、当前进度、最后推进时间和质量快照；读档后自动步骤继续计时，在场步骤继续等待原厨师抵达，不重复扣食材。
- Task 来源重建由协调器统一投影：领取中与在场执行中的步骤恢复活动角色绑定，无人值守执行中的步骤不继续占用角色，已完成步骤不重建临时 Task。
## R5-06：半成品、餐盘与装盘成品

- 新增独立 `KitchenProductModule`。半成品使用确定性唯一实例 ID，保存所属订单、单份餐点执行实例、来源步骤、物品与数量、备餐缓存槽位以及允许消费的直接后续步骤；不进入玩家公共库存，也不能跨餐点或跨订单领取。
- 厨房步骤领取时先预订直接前置半成品。最终装盘步骤还会同时预订飞艇餐盘架中的一个干净餐盘和飞艇交换站出餐区的一个餐点容量；无盘或出餐区已满时不占工作位、不消耗半成品，Task 保持等待。
- 步骤真正开始时，半成品状态与 KitchenFacility 缓存槽位一起由占用转为消费并释放槽位；装盘餐盘通过 Dishware 从 clean 原子转为 in_use，并保持唯一餐盘实例和成品绑定。
- 非最终步骤完成后，把 KitchenFacility 已占用缓存声明落成半成品实例；同一来源步骤重复完成不会创建第二份产物。已消费的半成品保留生命周期事实，但不再进入可领取读模型。
- 唯一叶子装盘步骤完成后才创建 Inventory 餐点实例。实例固定订单、订单行、单份餐点、食谱 ID/版本、餐盘、连续质量值和飞艇出餐位置；后续物流只需转移该实例位置，不重新计算质量。
- 最终质量按所有步骤启动时保存的 `weightedQuality / qualityWeight` 汇总；质量权重为零的装盘步骤不贡献质量。质量在装盘完成时冻结，不因等待运输或上菜改变。
- KitchenStepExecution 通过可选产物聚合接线保持向后兼容；正式组合启用后，成品创建成功会把对应单份餐点从 in-production 推进到 awaiting-pickup。
- 产物聚合状态、活动预订、半成品生命周期和成品质量全部进入版本化存档；恢复时交叉校验 RecipeExecution、Inventory 与 Dishware，重试完成操作不会重复创建成品或重复占用容量。
## R5-07：现实食谱只读模型

- 新增纯投影 `projectRecipeBookReadModel`，通过结构化 Content Port 同时读取每道菜的简化游戏食谱和详细现实食谱；Core 不反向依赖 Content 包，也不持有食谱册业务状态。
- 游戏层投影保留稳定食材 ID、整数数量、出品与价格信息、设备能力、在场规则以及步骤 DAG 的直接前置/后续、根步骤和最终步骤，供玩家理解游戏制作流程。
- 现实层投影只保留现实菜名、份量、人类可读配料用量、排序后的制作步骤和备注；盐、食用油等调味品没有 `itemId` 或整数业务数量，不可能进入库存、采购、订单预定或厨房扣料。
- `selectRecipeBookPage` 只在已经冻结的读模型上选择 gameplay 或 real-world 页签，不写回所选页签、不广播领域事件，也不引用 Inventory、Order 或 RecipeExecution。
- 投影对内容缺失、未知游戏食材和非法步骤引用快速失败；正式内容仍由 R2 构建期校验保证，运行时只消费已经生成的合法定义。
## R5-08：厨房确定性与阶段退出验收

- 修正厨房步骤跨越 tick 完成时刻：完成事实现在记录为“上次推进时刻＋尚需有效时长”，而不是本次外部观察时刻；大步推进和小步推进得到相同的步骤完成、后续开放与半成品产出时间。
- 新增粗粒度与细粒度对照测试。同一订单分别一次推进至 30 秒和按 5/10/15/20/30 秒推进，RecipeExecution 步骤状态、ready/completed 时间及 KitchenProduct 半成品时间完全一致。
- 新增 KitchenStepExecution 与 KitchenProduct 组合恢复测试：两个并行步骤部分推进后保存协调器和产物聚合，再从相同 RecipeExecution、KitchenFacility、Inventory、Order、Dishware 与 Movement 事实继续，步骤正常完成且食材不重复扣除。
- 阶段验收复用了 R5-04 的设备移动/升级占用边界、R5-05 的无人值守和超时释放、R5-06 的无盘/无出餐位等待及正式订单到已装盘餐点端到端测试；核心验收全程不依赖 Phaser 或动画回调。
- R5 阶段退出条件已满足：正式订单、整桌食材预定、食谱 DAG、设备工作位、厨师任务、半成品、餐盘、成品质量和现实食谱只读层均有独立权威状态与自动化验收。
## 当前边界

- RecipeExecution 决定 DAG 与步骤权威状态，KitchenFacility 决定工作位和实体缓存占用，KitchenProduct 决定半成品、餐盘绑定、装盘成品和最终质量，KitchenStepExecution 负责协调厨师、移动、扣料、计时、产品生命周期、订单状态与运行时 Task。
- 当前协调器保存步骤级加权质量事实，但不会提前汇总成最终餐点质量；半成品、餐盘、装盘成品及整份餐点质量由 R5-06 接入。
- 半成品、餐盘预定和成品实例由 R5-06 接入；步骤快照已经保留输入、输出和依赖信息供其消费。
- 上行在途来源由运行时配置为明确的物流位置；货梯的需求创建、方向和抵达处理仍由后续物流模块负责，Order 不读取货梯状态机。
- 小费比例的内容配置与服务员魅力计算将在服务流程接入时完成；Order 接收并锁定单份餐点已经计算出的整数小费事实。
