## 1. 依据与使用规则

依据文档：

- [飞艇餐厅功能模块需求确认清单 v0.1](./飞艇餐厅功能模块需求确认清单-v0.1.md)
- [飞艇餐厅重构架构设计 v0.1](./飞艇餐厅重构架构设计-v0.1.md)
- [飞艇餐厅 UI 布局与层级设计 v0.1](./飞艇餐厅UI布局与层级设计-v0.1.md)
- [飞艇餐厅 Godot 逐块重写技术方案 v0.1](./飞艇餐厅Godot逐块重写技术方案-v0.1.md)

执行规则：

1. R0—R12 记录 Electron 参考版本；新的正式开发严格按照 G0—G9 顺序推进。
2. 每个任务开始前检查依赖任务；完成时提交产出物、测试证据和未解决风险。
3. Electron 旧系统只允许必要修复，不继续增加新玩法；新玩法进入 Godot 重写计划。
4. 同一业务数据在迁移期只能有一个权威写入侧，禁止新旧实现双写。
5. Electron 改动继续运行相称的 npm 检查；Godot 改动运行 C# 测试、Godot 场景测试和可运行视觉验收。
6. 任何任务不得通过删除玩家数据、静默补物资、跳过业务节点或放宽断言让测试通过。
7. v1 静态内容以项目内 JSON 为唯一来源，不开放运行时 Mod 加载；如后续需要扩展，另行立项。

任务状态：`待开始`、`进行中`、`受阻`、`已完成`、`已归档`。

## 16. G0—G9：Godot 逐块重写

执行总规则：

1. 需求清单和本轮用户审核是新实现依据，旧代码只作参考。
2. 每块先展示可运行效果，再由用户确认；没有明确通过不得自动进入下一块。
3. 每块都允许删除或改写旧行为，不以旧版测试兼容作为默认完成条件。
4. 新 Godot 项目使用独立测试存档和用户数据目录，不读取或修改旧版玩家正式存档。
5. G0—G8 期间不删除旧 Electron 项目，也不建立双写或长期跨运行时桥接。
6. 只有当前阶段分解为可执行子任务；后一阶段在前一阶段审核通过后再细化，以避免提前固化未审核设计。

6. R0-06：建立旧系统冻结护栏。

R0 的目的不是证明旧玩法完全正确，而是记录当前可观察行为、保护已经验证的平台能力，并明确哪些旧行为将在后续阶段被已确认需求替换。R0 只允许增加清单、夹具、特征测试与冻结护栏，不修改经营规则或玩家可观察玩法。
