# 《空艇餐厅》Phaser + Electron 开发任务拆分

版本：v0.1
日期：2026-07-28
适用平台：Windows 10／11 x64
当前阶段：M0 技术验证完成，准备进入 M1 正式桌面壳

## 1. 拆分原则

- 以“能够运行和验收的纵向切片”为单位推进，不先铺开所有系统。
- 正式代码不继续堆叠在 `spikes/phaser-electron` 中；技术验证工程只作为参考和回归样例。
- 玩法逻辑、存档和时间推进放在纯 TypeScript 业务核心中，不依赖 Phaser 帧率。
- 正式美术不能成为 M1 的前置条件。M1 全部允许使用程序图形和占位资源。
- 从 M2 开始，每个里程碑同时交付代码、最小内容、美术接入和验收测试。
- 任何新增桌面视觉对象默认不可点击，只有显式注册进 `SemanticHitMap` 后才获得交互权。
- 离线阶段只结算经营事实，不触发、排队或补发剧情。

优先级定义：

- P0：里程碑无法完成时必须解决。
- P1：该里程碑应完成，但可在不影响主流程时短暂延后。
- P2：体验优化或发布前工作。

## 2. 总体里程碑

| 阶段 | 状态 | 可验收结果 |
| --- | --- | --- |
| M0 技术验证 | 已完成 | 透明窗口、不连续视觉、点击穿透、动态热区、输入锁与焦点策略得到验证 |
| M1 正式桌面壳 | 下一阶段 | 正式工程能够稳定显示桌面世界，打开管理窗口，并在双窗口间同步最小状态 |
| M2 最小经营闭环 | 待开始 | 玩家能够做一道菜、运输、售卖、保存，并获得无剧情的离线收益 |
| M3 食谱与首段情感体验 | 待开始 | 食谱成为故事载体，完成第一段可测试的角色与客人叙事 |
| M4 港口与中期成长 | 待开始 | 现实时间港口、贸易、捐赠、科技树和设施成长形成扩展循环 |
| M5 Windows 发布准备 | 待开始 | 完成打包、签名、性能、兼容性、恢复和发布检查 |

## 3. M0：技术验证收尾

M0 的关键结论已经通过，不再继续添加正式玩法。

### M0-01 验证基线归档（P0）

- 保留 `spikes/phaser-electron` 的可运行状态。
- 固定依赖版本和锁文件。
- 保留命中地图测试、技术验证记录和运行说明。
- 将原 Godot 代码明确标记为历史原型，不再承担新需求。

验收：

- 技术验证能够独立安装依赖、运行和执行 `npm run check`。
- README 能清楚区分正式方向、技术验证和历史 Godot 原型。

## 4. M1：正式桌面壳

目标：建立今后所有玩法都可以安全进入的正式客户端骨架。M1 不追求“好玩”，只追求架构、窗口与平台行为可靠。

### M1-01 正式工作区与构建骨架（P0）

- 建立根级单一工作区和单一锁文件。
- 创建 `apps/desktop`、`packages/core`、`packages/contracts`、`packages/content`、`packages/persistence` 和 `packages/test-support`。
- 设置共享 TypeScript strict 配置、路径别名、格式检查、类型检查和测试脚本。
- 建立桌面渲染器、管理渲染器和 preload 的独立构建入口。
- 明确开发构建与发布构建中的调试代码隔离规则。

验收：

- 一条命令可完成类型检查、单元测试和生产构建。
- `core` 不依赖 Electron、Phaser、React、DOM 或文件系统。
- 正式工程不从 spike 路径导入源代码。

### M1-02 Electron 主进程与应用生命周期（P0）

- 实现单实例锁、启动顺序和安全退出。
- 建立 `AppLifecycle`、`WindowManager`、`DisplayService` 和日志入口。
- 处理渲染器崩溃、窗口重建、系统退出和重复启动。
- 监听显示器增加、移除、DPI变化和工作区变化。

验收：

- 重复启动不会创建第二套桌面窗口。
- DesktopWindow 异常刷新不导致权威运行时丢失。
- 显示器发生变化后窗口不会留在不可见区域。

### M1-03 DesktopWindow（P0）

- 创建覆盖目标显示器 `workArea` 的透明、无边框窗口。
- 支持 `skipTaskbar`、非聚焦和玩家选择的置顶策略。
- 保持透明 Alpha 正确，不覆盖任务栏。
- 建立窗口尺寸、目标显示器和DPI变化后的布局重建流程。

验收：

- Windows 10／11 的 100%、125%、150%、200% 缩放下透明背景正确。
- 点击可交互对象时不抢走当前工作软件的键盘焦点。
- 任务栏位于四边或自动隐藏时，窗口仍使用正确工作区。

### M1-04 ManagementWindow（P0）

- 创建普通、不透明、可聚焦、可缩放的管理窗口。
- 设置、科技树、档案和图鉴共用一个 React 路由外壳。
- 保存窗口尺寸和位置，并在显示器变化后做越界恢复。
- 验证是否建立 `parent` 关系；在验证完成前保持可配置。

验收：

- 玩家主动打开时管理窗口正常获得焦点。
- 关闭管理窗口不会退出游戏，也不会强迫焦点回到 DesktopWindow。
- 管理窗口隐藏后停止不必要的 React 动画。

### M1-05 双 Preload 与类型化 IPC（P0）

- 为桌面窗口和管理窗口建立不同的 preload 入口。
- 建立共享的命令、事件、DTO和错误契约。
- 仅通过 `contextBridge` 暴露白名单函数。
- 校验 sender、通道、请求负载和订阅清理。
- 加入 IPC 契约单元测试。

验收：

- 渲染器无法访问原始 `ipcRenderer`、Node.js 和任意文件路径。
- 非法命令得到结构化拒绝，不会使主进程崩溃。
- 窗口销毁后不存在残留订阅。

### M1-06 GameRuntime 最小状态骨架（P0）

- 建立可序列化的最小 `GameSnapshot`。
- 建立 `CommandRouter`、`DomainEvent` 和状态广播流程。
- 使用可注入时钟和随机数接口。
- 用一个演示命令验证“提交命令—主进程校验—状态变化—双窗口刷新”。

验收：

- Phaser 和 React 看到同一份权威状态。
- 刷新任一渲染器不会重置状态。
- 渲染器只能提交命令，不能直接修改权威对象。

### M1-07 SemanticHitMap 正式迁移（P0）

- 将矩形、圆形、多边形热区迁入正式 `contracts` 和桌面渲染器。
- 实现 `PASS_THROUGH`、`INTERACTIVE`、`CAPTURE_LOCK` 状态机。
- 支持动态注册、撤销、优先级、禁用和组件卸载清理。
- 加入飞艇多边形、餐厅矩形和临时气泡的测试。
- 加入动态对象经过静止光标时的重新判定。

验收：

- 中央角色、缆车、云雾和特效始终穿透。
- 飞艇只有简化轮廓内可以点击。
- 临时面板关闭后立即撤销热区。
- `pointerdown` 到 `pointerup` 期间不会把后半次输入落到后方应用。

### M1-08 Phaser 场景骨架（P0）

- 建立 `BootScene`、`DesktopWorldScene`、`EnvironmentScene`、`DesktopUiScene`。
- 开发构建加入 `InteractionDebugScene`。
- 使用程序图形或占位图显示飞艇、餐厅、港口预留位置、角色和缆车。
- 建立响应式布局，使所有对象按目标显示器工作区重新定位。

验收：

- 场景负责表现，不包含库存、烹饪或剧情规则。
- 可随时显示命中区域、鼠标DIP坐标和穿透状态。
- 环境场景可以整体休眠，不影响运行时状态。

### M1-09 首次启动与设置保存（P0）

- 首次启动通过普通窗口选择目标显示器和是否置顶。
- 提供正常、安静、降低动态三种表现设置的最小入口。
- 保存窗口、显示器、缩放和置顶设置。
- 设置变化能够安全地实时应用到 DesktopWindow。

验收：

- 首次启动不要求在不可聚焦透明窗口里输入。
- 重启后设置正确恢复。
- 原目标显示器不存在时回退到当前主显示器，并提示玩家重新选择。

### M1-10 最小 React Flow 科技树验证页（P1）

- 创建 6—10 个假数据节点。
- 展示锁定、可购买、已购买和前置不足状态。
- 通过 IPC 提交演示购买命令。
- 购买后 Phaser 桌面世界产生一个可见但不影响玩法的状态变化。

验收：

- 双窗口状态同步稳定。
- React Flow 只负责展示，购买校验发生在 GameRuntime。
- 管理窗口刷新后节点状态不丢失。

### M1-11 平台回归与常驻测试（P0）

- 建立 Windows 10／11、DPI、任务栏位置、多显示器和焦点测试清单。
- 执行睡眠、锁屏、恢复和显示器热插拔测试。
- 执行 2 小时常驻测试，记录内存、GPU、句柄和 IPC 订阅变化。
- 检查 Steam Overlay、录屏和全屏应用的基础层级行为。

M1 退出条件：

- 正式工程可以稳定启动、退出和重启。
- 透明桌面世界与普通管理窗口同时工作。
- 动态点击穿透、输入锁和焦点策略通过平台矩阵。
- 双窗口通过类型化 IPC 同步权威状态。
- 设置能够保存和恢复。

## 5. M2：最小经营闭环

目标：使用占位美术完成“食材—做饭—运输—餐厅售卖—收益—保存／离线结算”的完整循环。

### M2-01 GameClock 与确定性模拟（P0）

- 在线玩法使用低频逻辑 Tick。
- 所有长任务保存 `startedAtUtc` 和 `finishAtUtc`。
- 使用可注入 UTC 时钟，处理系统时间回拨。
- 建立固定种子随机数和 1 小时、24 小时、超长离线模拟测试。

### M2-02 最小内容定义（P0）

- 定义 3—5 种食材、2—3 道食谱、1 种货币和基础设施。
- 建立稳定 ID、引用校验和运行时内容加载。
- 暂不建立完整编辑器，内容先使用受校验的 JSON／TypeScript 数据。

### M2-03 InventorySystem（P0）

- 实现容器、容量、数量、预留和原子转移。
- 支持厨房、缆车、餐厅三个库存位置。
- 加入不足、容量满、重复提交和失败回滚测试。

### M2-04 CookingSystem（P0）

- 实现食谱校验、食材预留、单队列、完成时间和产出。
- 动画只响应 `cooking.started`／`cooking.completed`，不决定完成时间。
- 第一版只提供“开始一道菜”的简单操作。

### M2-05 LogisticsSystem（P0）

- 实现厨房到餐厅的运输请求、清单和到达时间。
- 让缆车 Tween 追随逻辑状态，但低帧率或跳过动画不改变结果。
- 处理目标库存已满和重复到达。

### M2-06 RestaurantSystem（P0）

- 生成低压力客人和订单。
- 完成上菜、铜币收入和基础满意度。
- 普通客人离开不制造惩罚，也不要求即时处理。

### M2-07 SaveService 与无上限离线结算（P0）

- 定义带版本号的存档信封、校验、临时文件和原子替换。
- 建立备份、损坏回退和最小迁移框架。
- 离线结算使用批量或闭式算法，禁止逐秒循环。
- M2 离线结算不调用 NarrativeSystem。

### M2-08 最小经营界面与桌面反馈（P1）

- 飞艇入口显示食材和烹饪队列。
- 餐厅入口显示库存、订单和收入。
- 中央缆车、角色做饭和客人等待继续保持不可点击。
- 管理窗口提供调试用库存与时钟页面。

### M2-09 M2 自动化与稳定性（P0）

- 覆盖库存原子性、烹饪队列、运输、售卖、保存和离线一致性。
- 执行 8 小时模拟与至少 2 小时真实常驻测试。

M2 退出条件：

- 新存档能够完成至少一道菜的完整生产与销售。
- 退出、重启和离线后，经营结果一致且不会重复结算。
- 断网不会影响基础玩法。
- 整个闭环可以使用占位美术完成。

## 6. M3：食谱与首段情感体验

目标：证明“食谱是情感载体”，而不只是配方数据。

### M3-01 ContentRegistry 与内容校验（P0）

- 完成 Item、Recipe、Customer、Character、StoryEvent 和本地化定义。
- 校验稳定 ID、引用、本地化键和故事条件。
- 输出编剧／策划可读的校验错误。

### M3-02 NarrativeSystem（P0）

- 实现在线叙事条件、去重、排序、完成和回看。
- 支持短对话、便签、信件、回忆和食谱日志。
- 明确离线结算无法调用故事解锁入口。

### M3-03 食谱日志（P0）

- 每道关键食谱同时保存配方信息、人物来源和情感记录。
- 支持食谱初次发现、后续补充和故事回看。
- 食谱解锁与经营可用性、故事可读性分别建模。

### M3-04 首段纵向叙事切片（P0）

- 确定第一位主角、第一位客人和第一道情感食谱。
- 编排玩家首次 15—30 分钟体验。
- 包含一次经营行为、一次人物互动和一次食谱意义变化。
- 错过提示时允许稍后查看，不制造限时焦虑。

### M3-05 第一批正式美术接入（P1）

- 接入主飞艇／厨房、底部餐厅、主角和第一位客人。
- 接入首道情感食谱卡片、基础UI和少量环境动画。
- 为飞艇美术导出简化点击多边形。
- 占位素材可继续用于非核心物件。

### M3-06 叙事回归测试（P0）

- 测试故事条件、重复触发、读档恢复和内容版本迁移。
- 证明离线跨过事件时不会补发剧情。
- 完成至少一轮外部试玩记录。

M3 退出条件：

- 玩家能够清楚理解一张食谱与角色关系的变化。
- 首段剧情可完整开始、暂停、恢复和回看。
- 离线规则与情感节奏不冲突。

## 7. M4：港口与中期成长

目标：让餐厅与外部世界发生联系，建立贸易、捐赠、来客故事和科技成长。

### M4-01 PortSystem 与 DockScheduler（P0）

- 使用 UTC 现实时间调度普通来访飞艇和有效停靠窗口。
- 玩家离线错过的普通贸易会话无惩罚略过。
- 叙事来访只能在在线状态下解锁，不离线补发。

### M4-02 TradeSystem（P0）

- 实现访客购买食物、出售异地物资和交易报价。
- 交易通过库存原子转移与运输请求完成。
- 重要报价允许稍后处理，避免短时限压力。

### M4-03 DonationSystem（P0）

- 实现食物选择、校验、封装、派发和历史记录。
- 捐赠只产生事实条件，不直接生成战争场景或信件正文。
- 不捐赠不施加简单道德惩罚。

### M4-04 ProgressionSystem 与正式科技树（P0）

- 实现前置依赖、费用、购买、效果和功能解锁。
- 接入正式 React Flow 节点数据。
- 覆盖容量、速度、航线、港口和内容解锁效果。

### M4-05 FacilitySystem／LayoutSystem（P1）

- 管理飞艇修复阶段、设施槽位和餐厅布局。
- 布局变化触发表现重建和命中地图失效。
- 验证底部餐厅最终高度与收起／低活跃状态。

### M4-06 港口叙事与美术（P1）

- 制作港口主体、停靠飞艇、装卸和贸易反馈。
- 港口主体可点击，来访飞艇和越界特效默认穿透。
- 完成至少一条“贸易故事”和一条“捐赠后续回响”。

### M4-07 多窗口状态压力测试（P0）

- 大量科技节点、港口状态和经营事件同时变化时保持同步。
- 管理窗口崩溃、关闭或刷新不影响桌面模拟。
- 管理窗口隐藏时停止 React Flow 布局计算。

M4 退出条件：

- 现实时间港口可以稳定到访和恢复。
- 贸易、捐赠和成长系统都能改变后续经营。
- 港口故事不会因离线而错误触发或丢失经营结算。

## 8. M5：Windows 发布准备

### M5-01 PerformanceGovernor（P0）

- 实现正常、安静、降低动态和桌面静止档位。
- 控制帧率、粒子、环境动作、React动画和资源加载。
- 权威模拟精度不随表现档位变化。

### M5-02 托盘、启动与通知（P1）

- 提供显示／隐藏、设置、安静模式和退出入口。
- 评估开机启动默认值和首次授权说明。
- 所有系统通知和声音提醒均由玩家显式选择。

### M5-03 打包、签名与 Steam（P0）

- 锁定 Electron Forge maker 和 Windows 安装包格式。
- 配置代码签名、应用图标、版本信息和卸载行为。
- 验证 Steam 启动、Overlay、截图、云存档边界和更新策略。

### M5-04 存档迁移与崩溃恢复（P0）

- 完成旧版本存档迁移、备份轮换和损坏提示。
- 验证强制退出、断电模拟和渲染器崩溃后的恢复。
- 日志不得记录剧情选择、系统路径等不必要隐私信息。

### M5-05 发布兼容性矩阵（P0）

- Windows 10／11、主流DPI、多显示器、四边任务栏。
- 睡眠、锁屏、RDP、热插拔、全屏应用、录屏与Overlay。
- 8小时和隔夜常驻，检查工作集、GPU内存、句柄、订阅和日志增长。

### M5-06 内容、授权与可访问性检查（P0）

- 建立全部美术、字体、音频和代码依赖的授权台账。
- 加入降低动态、字号／缩放、颜色可读性和音量选项。
- 检查署名页、第三方许可、隐私说明和商店素材。

M5 退出条件：

- 候选版本通过自动测试、平台矩阵和隔夜常驻测试。
- 安装、升级、卸载和存档迁移可重复验证。
- 发布包不携带开发调试入口、原始付费素材包或未授权资源。

## 9. 美术与视觉任务流

美术工作与程序开发并行，但正式美术从 M2 后半段开始进入关键路径。

### ART-01 美术规范（M1期间，P0）

- 选择像素、手绘卡通或剪纸／木偶式2D中的一种。
- 固定侧视视角、角色比例、描边、光源、色板和动画帧率。
- 固定资产命名、透明边距、锚点、导出倍率和图集规则。
- 定义黄铜／铜、深蓝、暖琥珀和天空冷色的使用范围。

### ART-02 资源授权台账（M1期间，P0）

每项外部资源记录：

- 名称、作者、来源链接和购买记录；
- 许可证版本、商用与修改权限；
- 署名文本；
- 是否经过修改；
- 本地许可证副本；
- 是否为AI辅助资产及其生成记录。

### ART-03 M2占位资源包（P0）

- 程序绘制飞艇、餐厅和港口预留轮廓。
- 1个占位角色、1辆缆车、3—5种食材和2—3道菜。
- 优先保证尺寸、锚点、命中轮廓和图集接入流程，不追求最终品质。

### ART-04 M3核心定制资源（P0）

- 主飞艇／厨房、主角、底部餐厅、第一位客人。
- 主角待机、做饭、搬运和休息的最小循环动画。
- 第一张情感食谱卡与剧情表现素材。

### ART-05 程序视觉效果（M2—M5，P1）

- 云层视差、蒸汽、火星、炉火、灯光和天气。
- 缆车轻微晃动、绳索运动和飞艇停靠尾流。
- 所有效果默认穿透，并服从安静和降低动态设置。

## 10. 设计与内容前置任务

这些问题不阻塞 M1 工程骨架，但必须在对应里程碑前确认。

### 进入 M2 前

- 确认底部餐厅原型高度和是否允许收起。
- 确认缆车位于左侧、右侧或由玩家选择。
- 确认最小食材、食谱、制作时长和收入数值。
- 确认玩家第一次主动操作发生在飞艇还是餐厅。

### 进入 M3 前

- 确认主角、第一位客人和第一道情感食谱。
- 写出首次 15—30 分钟的体验脚本。
- 确认对话、便签、信件和食谱日志各自承担的内容。

### 进入 M4 前

- 确认港口位于哪一侧以及打开时的视觉占用范围。
- 确认普通来访飞艇的现实时间频率和停靠时长。
- 确认贸易是否包含异地食材、零件和食谱残页。
- 确认捐赠会影响哪些人物故事、地区状态和长期结局。
