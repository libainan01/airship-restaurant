# 飞艇餐厅 R4 角色阶段实现记录 v0.1

> 历史阶段记录：本文保留 R4 当时的角色迁移与表现层命名。原 NPC Director 已在 R8 改为只读 `RestaurantNpcProjector`；当前实现见《飞艇餐厅当前技术架构 v0.1》。

## R4-01：统一 Character 模块

- NPC、厨师、奥托、剧情顾客和普通员工共享同一种 CharacterInstanceState，身份用途不再决定对象类型。
- 每个角色统一保存五项技能：烹饪、魅力、移动、修理、飞艇驾驶。
- 技能只通过实际工作或训练增加对应经验，不设置通用技能点；每级暂以 100 经验作为核心规则，等级上限 100。
- 天赋由独立天赋库校验。角色最多三个天赋；专属天赋只能交给指定剧情角色；普通天赋抽取会排除专属天赋且不会重复。
- 天赋抽取只负责生成初始结果，实际分配保存在角色状态中，读档不会重抽。
- coreMember 是稳定角色事实，解雇限制将在 R4-02 的雇佣模块中消费，不与顾客/员工临时身份混合。
- Character 支持幂等操作、版本化状态、事务回滚、领域完成事件与只读组合模型。

## 内容与启动装配

- 当前角色和天赋 JSON 可直接映射到 Character 模块。
- 新游戏默认创建白夜城与奥托两个核心角色实例。
- 玛莎、托马斯等剧情顾客可由相同模块创建，不需要顾客专用角色类。
- 顾客、员工、职位和当班状态将在 R4-02 作为角色之上的关系与派生标签实现，不回填到 Character 基础身份。

## R4-02：雇佣、职位与日程

- 雇佣名册永久保存核心成员或普通招募员工关系，但不永久保存“员工”标签。
- 角色可掌握多个职位，只有一个主职位；切换主职位只允许选择已经掌握的职位，并由后续 Task 模块用作优先级加权。
- Demo 每名员工使用一个连续日班；同时支持跨午夜的连续班次。
- “员工”标签只在班次内派生；班次外的角色可由来访事实派生“顾客”标签，两者不会同时出现。
- 船长使用独立的 captain-qualified 资格，不受餐厅班次限制；出航占用期间不可领取新任务，返航后立即恢复资格，不保存个人冷却。
- 解雇普通员工后立即停止领取新任务；如当前工作必须完成则进入待解雇状态，任务完成后正式移出名册。核心成员始终拒绝解雇。
- 白夜城默认掌握并主职厨师；奥托默认掌握服务员和本地采购员，主职服务员。
- Employment 支持版本化存档、幂等命令、事务回滚、完成事件和员工管理读模型。

## R4-03：通用 Task 模块

- 统一任务生命周期为等待、执行中、完成、失败、取消和已中断。
- 任务声明来源、目标、标签、可执行职位、最低技能、基础优先级、紧急度和是否允许中断。
- 调度先执行标签、职位、技能和角色可用性硬过滤，再计算优先分数。
- 优先分数由基础值、主职位加成、等待时间加成、紧急度和移动距离成本组成；相同分数按创建时间与稳定任务 ID 排序。
- 兼职职位保留任务资格，主职位只影响加权，不直接启动任务或绕过任务池。
- 任务领取同时锁定任务和执行角色，避免多人领取同一任务或一个角色同时执行多个任务。
- 自动抢占只允许严格更高优先级的紧急任务打断当前可中断任务；通用模块不负责保留进度或重试。
- 完成、失败、取消和中断都发布生命周期广播；完成广播明确携带任务、类型、角色、来源、目标、完成时间和结果。
- Character 与 Employment 的只读事实通过独立投影生成 TaskCandidate，顾客身份不能凭技能或职位绕过员工标签。
- Task 支持版本化状态、幂等操作、事务回滚和读模型。

R4-03 完成后的全项目验证：97 个 Vitest 文件、414 项测试、4 项 Node 测试全部通过，类型、内容、架构和生产构建均通过。

## R4-04：任务来源重建

- taskId 被明确约束为稳定来源键，由来源对象、任务类型、目标对象和业务阶段标识确定，不使用随机运行序号。
- Task 模块的持久化格式只保存模块 revision 与幂等操作历史，不保存等待队列、候选角色、优先级缓存、终态记录或执行绑定。
- 等待任务由订单、餐桌、食谱、维修、运输等权威业务来源在读档后重新投影。
- 已开始任务的执行角色与领取时间也由来源模块保存并投影，Task 不复制拥有这些业务事实。
- 完成后的业务来源停止投影任务，因此读档不会重新创建已经完成的工作。
- 多个来源产生相同稳定键会立即拒绝恢复，避免静默覆盖或重复任务。
- 恢复过程不重放 task.created 或 task.claimed 等运行时事件；恢复后重新计算动态优先级。
- 已开始任务恢复后仍锁定执行角色，其他等待任务不能被同一角色重复领取。

R4-04 完成后的全项目验证：98 个 Vitest 文件、420 项测试、4 项 Node 测试全部通过，类型、内容、架构和生产构建均通过。

## R4-05：Movement 与动态交互站位

- 角色移动状态独立保存导航区域、2D 逻辑坐标、目标引用、当前计划、交互预订和阻塞原因。
- 区域内采用可替换的 NavigationPlanner；Demo 默认使用直线移动，桌椅和厨房设备不作为硬寻路障碍。
- 任务只提供目标引用和可选交互要求，不保存固定会话点或建筑旧坐标。
- 目标可以提供多个交互矩形及各自容量；Movement 按容量、可达性、距离和稳定 ID 选择。
- 角色已经位于合法交互区域时原地进入 arrived，不先离座再跑向固定点。
- 交互位置在开始移动时预订；任务释放、预订超时或阻塞时释放容量。
- 所有候选点不可达时返回明确结果，不使用瞬移兜底；目标位于其他导航区域时返回 REGION_CONNECTION_REQUIRED。
- SceneLayout 只读适配器按最新布局 revision 解析建筑当前交互区域；玩家移动建筑后角色重新规划到新位置。
- 成功的建筑目标重定位不会累计寻路失败次数；真实预订超时才计入有限重试。
- 普通闲聊只检查角色是否已经处于同一区域和自然交流距离，不创建 Movement 计划。
- Movement 到达只广播移动事实，不完成业务任务；任务完成仍由对应执行器决定。
- Movement 支持版本化状态、事务回滚、幂等操作和表现读模型。

R4-05 完成后的全项目验证：100 个 Vitest 文件、429 项测试、4 项 Node 测试全部通过，类型、内容、架构和生产构建均通过。

## R4-06：单人人员电梯

- 人员电梯是独立角色运输实例，仅连接地面与飞艇两个导航区域，不提供物资或货物 API。
- 完整跨区计划包含步行到候梯点、等待、乘梯、到站离梯和从出口继续步行。
- 轿厢只在存在乘梯请求时移动；停在另一端时会空载前来接第一名乘客，不进行无意义空载巡航。
- 候梯请求严格按进入队列顺序处理，一次只允许一个活动请求和一名乘客。
- 轿厢开始移动后，新请求只能进入队尾，不能途中加入或替换当前乘客。
- 上梯、载客移动和下梯具有独立配置时长；轿厢阶段与插值进度通过只读快照公开。
- 完成广播携带角色、目标导航区域和出口坐标；Movement 接收后更新区域，再重新解析原任务目标继续移动。
- 电梯不直接完成 Task，也不读取物资货梯数量、速度或科技。
- 请求与推进使用单调模拟时钟，迟到请求不会从旧推进时间倒算并瞬间完成。
- 队列、活动请求、乘客、轿厢位置和阶段时间全部进入版本化状态，移动中保存恢复后可连续推进。
- 模块支持幂等命令、事务回滚和完整生命周期广播。

R4-06 完成后的全项目验证：102 个 Vitest 文件、437 项测试、4 项 Node 测试全部通过，类型、内容、架构和生产构建均通过。

## R4-07：角色表现读模型

- 新增独立的 `characters` 运行时读模型切片，与 `layout`、`inventory` 通过相同的注册、订阅、修订号和 IPC 通道发布。
- 单个角色表现项组合统一身份、姓名、核心成员事实、导航区域、2D 逻辑坐标、动作、目标、执行中任务摘要、派生身份标签、主职位和人员电梯请求。
- 动作语义由 Core 统一投影为静止、移动、交互、阻塞、候梯、上梯、乘梯和下梯；人员电梯阶段优先于普通移动与任务动作。
- 人员电梯表现包含轿厢阶段、阶段起止时间、当前插值进度、所在站点、移动起终点、乘客、活动请求和候梯队列。
- 读模型源只依据 Character、Employment、Task、Movement 和 PersonnelElevator 的公开只读模型组合，不读取 Phaser Actor，也不复制业务所有权。
- 白夜城与奥托在桌面主进程启动时进入统一 R4 角色组合，并由同一 `characters` 切片发布。
- Phaser 侧新增纯表现插值器：收到新逻辑坐标后只平滑位置和选择动画，不调用任务完成、移动到达或电梯推进 API。
- `characters` 更新不会触发静态建筑与背景重绘；旧运行时兼容模式会提供合法的空角色切片，旧存档和测试桥接保持可用。
- 当前过渡阶段仅用新读模型覆盖白夜城与奥托的表现；顾客服务队列与旧业务阶段仍留在 RestaurantNpcDirector，统一在 R4-08 移除，避免在 R4-07 同时改写订单业务。

R4-07 完成后的全项目验证：104 个 Vitest 文件、440 项测试、4 项 Node 测试全部通过；R0 冻结护栏、依赖边界、内容校验、类型检查和生产构建均通过。构建仅保留既有的 Vite 大包提示。

## R4-08：收缩 RestaurantNpcDirector

- `RestaurantNpcDirector` 已改为无业务推进的纯快照投影：相同餐厅快照、角色读模型和对白输入可在新实例中重建出相同 Actor 帧。
- 顾客 Actor 直接由 Core 的 `activeCustomer`、`diningCustomers`、顾客阶段和已解锁座位生成；renderer 不再复制顾客阶段、离店状态或服务队列。
- 顾客的浏览菜单、呼叫、点单、等待和用餐动作只映射 Core 已确认的业务阶段，不在动画时间到达时推进订单。
- 奥托只有在 characters 读模型明确包含接单或送餐任务摘要时才显示对应服务提示；顾客进入某个阶段不会再让 renderer 擅自替奥托选任务。
- 对话参与者优先绑定当前自然位置上的真实顾客或核心角色；未知剧情说话人只创建临时表现 Actor，不生成移动任务或固定会话站位。
- 闲聊机会改由 `GameRuntime.tick()` 根据真实在店/用餐顾客事实自动生成，renderer 不再调用 `dialogue.request-ambient`。
- 已移除 WorkspaceScene 中的闲聊命令协调器，并删除不再使用的 `restaurant-dialogue-request-coordinator.ts` 及其测试。
- R0 护栏新增“纯表现 Director”分类，禁止其依赖服务任务队列、奥托服务协调器、顾客事件协调器、顾客生命周期协调器、`dispatchCommand` 或 Task 写入 API。
- Director 从 renderer 遗留业务文件清单移出；旧闲聊命令协调器同步移除后，遗留登记由 18 个降至 16 个。其余旧文件不再位于运行路径，将按 R6-10 统一物理清理。

R4-08 完成后的全项目验证：103 个 Vitest 文件、431 项测试、4 项 Node 测试全部通过；R0 冻结护栏、依赖边界、内容校验、类型检查和生产构建均通过。桌面生产包由约 1,472 kB 降至约 1,436 kB，仅保留既有的 Vite 大包提示。
