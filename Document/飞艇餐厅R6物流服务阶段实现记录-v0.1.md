# 飞艇餐厅 R6 物流服务阶段实现记录 v0.1

> 历史阶段记录：本文保留 R6 当时的兼容门面、总快照投影和表现层命名。相关兼容边界已在 R8 删除，NPC 表现已改为只读 Projector；当前实现见《飞艇餐厅当前技术架构 v0.1》。

## R6-01：Logistics 运输需求

- 新增独立 `LogisticsDemandModule`，统一保存地面交换站与飞艇交换站之间的双向运输需求组；业务模块只发布需求，不直接控制货梯实例、路线或动画。
- 需求类型固定为已装盘餐点、订单阻塞物资、玩家手动运输和普通补给。基础优先级依次降低；同级等待更久者优先，非餐点需求可随等待时间提权，但永远不能超过已装盘餐点。
- 普通补给同级时先处理目标覆盖率更低的组；玩家创建的同向和反向手动组彼此独立，不合并、不抵消，并可调整尚未领取的剩余数量与队列顺序。
- 货梯调度每次只领取一个单位，不提前锁定整组数量。领取在同一流程中锁定一个来源单位和一个目的仓位；目的仓位失败时立即释放本次新建的来源预定，不留下半套预定。
- 订单已经持有的食材预定可被物流需求引用，领取时按活动单件租约计数，不重复预定同一库存；普通物资则由 Logistics 为当前单件建立独立来源预定。
- 来源不足与目标仓位不足分别形成 `WAITING_SOURCE` 和 `WAITING_CAPACITY`。需求组保持活动，不分配货梯；阻塞、恢复等原因变化广播独立领域事件，供后续调度与 UI 接入。
- 手动运输数量可以大于当前库存。缺货时保留需求等待；玩家将剩余数量改为零或停止需求时，只取消尚未领取部分，已经领取的单件继续完成。
- 版本化状态保存需求组、活动单件租约和幂等操作记录；读档恢复不会复制需求、来源预定、目的容量预定或在途单件。

## R6-02：小型货梯实例组

- 新增独立 `FreightElevatorModule`，每台货梯保存唯一 ID、专属单件在途库存位置、停靠端、三态行程、当前 Logistics 单件租约、货物实例、路线/速度快照、耐久与维修事实；Demo 基础数量通过四实例夹具验证。
- 多台空闲货梯按稳定顺序共享 R6-01 需求池并原子领取不同单件。货梯停靠在来源端时直接自动装货，停靠在另一端时只为已领取需求进行一次空载调位；没有有效需求时保持停靠，不循环空载。
- 堆叠食材通过 Inventory 拆成唯一单件在途实例，餐盘和成品餐点沿用原实例；装卸只改变 Inventory 权威位置。成品的订单、质量、餐盘和其他属性不重建、不复制。
- 空载与载货行程按“路线长度÷本段开始时速度”锁定耗时；配置速度变化只影响下一段。粗粒度推进会在精确抵达时刻连续处理装卸和下一段，与逐段推进得到相同业务结果。
- 每完成一段移动才扣耐久，途中不会故障。空载调位后即使耐久归零，已经领取的单件仍完成载货行程；完成后停靠并停止领取新需求。
- 货梯首次出现损耗即生成稳定维修 TaskSource，不必等到故障。等待任务限定员工和维修员职位，并要求修理能力；开工时冻结修理能力为本次维修速度，进行中的角色绑定与剩余时间进入存档。
- 编辑模式冻结运输与维修。确认布局时按冻结前归一化行程比例映射新路线并重算剩余时长；取消编辑只平移冻结期间的时间，不产生运输状态事件。
- 读档交叉校验货梯状态、Logistics 活动租约和 Inventory 货物位置。载货行程、空载调位及维修从原进度继续，不重新领取、不复制货物、不重放已完成事件。

## R6-03：本地采购与采购小车

- 新增独立 `LocalProcurementModule`。自由采购和按食谱采购共用一份草稿；按食谱采购只读取游戏流程使用的简化整数配料，不把现实食谱的克数、调味品或制作说明带入库存计算。
- 食谱建议量按“需求量－地面可用未预定库存－尚未到货的本地采购量”计算并钳制为零；自由采购在建议量之上累加，玩家仍可用最终覆盖量明确修改提交结果。
- 每项食材默认选择实际单价最低的供应商，同价时选择往返更快者，也支持玩家显式覆盖货源。下单时以所有在岗本地采购员中最高魅力锁定价格；无人具备资格时使用基础价格。
- 整份草稿提交通过跨模块事务一次性付款并建立供应商订单。余额不足或任一校验失败时，Finance 与采购状态一同回滚，不会留下扣款、空订单或半批次。
- 订单按下单当刻的小车载量固定拆批；供应商备货并行且不占用人员和车辆。备货完成后才发布稳定采购 Task，要求在岗员工、本地采购员职位和空闲采购小车。
- 小车开工时冻结本次速度和往返时长；途中不可中断，角色移动速度不参与计算。返程抵达时在同一事务内将货物加入地面交换站、完成 Task、释放小车并推进批次和订单状态。
- 采购小车的容量和速度属于实例状态，读档以存档实例属性为准，以支持后续实例升级；已经创建的批次保留容量快照，已经出发的行程保留速度快照，升级只影响后续业务边界。
- 版本化状态保存草稿外的正式订单、批次、小车占用和幂等键。读档后备货、等待任务和在途行程原地续行，不重复付款、建单、创建任务或入库。

## R6-04：Customer 完整来访

- 新增独立 `CustomerModule`，保存本次来访的顾客组、临时顾客资格、候位槽、餐桌与座位预订、来访阶段、待提交/正式订单引用、逐份用餐计时、结账观察和离店结果；Character 仍只保存统一人物身份。
- 等候区和餐桌通过 `CustomerVenuePort` 提供稳定场景能力 ID。候位容量按人数占用；顾客组不拆分、不拼桌，按最早到达顺序选择容量最小且足够的干净空桌，已预订桌的剩余座位不再分配。
- 桌位移动或建筑样式变化不改变稳定桌位、座位和候位 ID；空闲新桌可在刷新时加入匹配，已占用桌的座位结构若被非法改变会明确拒绝恢复，不通过静默搬移掩盖状态错误。
- 菜单查询逐项复用 Order 的食材可用性检查；缺少未预定食材的菜品对顾客不可点。桌边记录整桌选择时再次检查组合数量，并由现有 Order 原子预定食材，只形成一桌一份待提交点单。
- Customer 不直接把待提交点单变成正式订单。服务员后续必须在 R6-05 前往地面订单传递点；Order 正式提交并通知厨房后，Customer 只观察稳定订单引用并进入用餐阶段。
- 每份已送达餐点独立锁定开始和结束时间，顾客按单品陆续用餐；等待点单、上菜或结账没有取消、满意度衰减或催促倒计时。全部餐点食用后进入等待结账。
- Order 完成唯一结算后，Customer 将餐桌标记为脏桌并进入离店阶段；顾客离店释放座位和顾客资格，但脏桌仍不可分配，直到后续清桌任务明确完成后才重新匹配候位组。
- 闲聊只读取当前来访上下文和餐桌，返回 `requiresMovement: false`，不会修改桌位、阶段或订单。正在顾客来访的角色即使跨过上班时间也只保留顾客资格，离店后才重新按日程获得员工资格。
- 版本化存档交叉校验顾客、桌位、候位、待提交订单和正式订单引用；用餐中读档继续原计时，已经食用、结账或离店的事实不会重复广播或结算。

## R6-05：Service 任务来源

- 新增独立 `ServiceModule`，把 Customer 与 Order 的权威事实投影为接待、桌边点单与地面传单、餐点领取与送达、结账和清桌五类稳定 TaskSource；等待队列和优先级缓存仍不进入 Service 存档。
- 所有任务要求当前员工标签和服务员职位，主职位加权、等待提权、距离成本及稳定并列顺序继续由通用 Task 计算，Service 不建立第二套角色调度器。
- 餐点领取/送达位于订单阻塞层，基础优先级高于结账清桌；结账清桌高于新客接待点单。有顾客排队且没有干净空桌时，清桌任务标记为紧急并增加动态紧迫度。
- 接待完成后才开放同一来访的桌边点单任务。桌边记录会通过 Customer/Order 原子预定整桌食材，并立即把当前工作流切换为不可中断的传单阶段；抵达地面订单传递点并提交后才完成同一 Task、创建正式订单并通知厨房。
- 结账工作流调用 Order 的唯一结算批次，完成后广播通用 `task.completed` 和 Service 结账事件；Customer 随后观察结算并进入离店、脏桌阶段。
- 取送餐和清桌采用外部交付协议：R6-06/R6-07 必须先原子推进 Inventory/Order 或 Dishware/Customer 权威来源，Service 确认原来源任务已经消失后才允许完成 Task，禁止“动画完成即业务完成”。
- `ServiceMealPickupPort` 明确隔离“已经装盘”和“已经抵达地面”：只有地面取餐端口确认可领取的 `awaiting-pickup` 餐点才发布服务任务，避免服务员从飞艇隔空取餐。
- Service 存档只保存已领取工作流的角色绑定、原始稳定任务请求、领取时刻、必要阶段和待提交订单引用；Task 读档可从 Service 快照恢复活动绑定与等待任务，不重复领取或完成。

## R6-06：托盘与地面取送餐

- 新增独立 `TrayDeliveryModule`，以 R6-05 已领取的送餐工作流为批次主任务；只有地面交换站中真实存在、库存分类为餐点且 `mealId` 与 Order 匹配的唯一实例可以进入托盘。
- Order 新增跨 Inventory 的原子批量取餐边界：整批先校验餐点状态、实例身份、来源位置和目标容量，再在同一事务中把实例移动到服务员携带位置并把餐点推进为 `in-transit`。任一份失败时，库存、订单状态和幂等记录全部回滚。
- 托盘容量在每次取餐时形成快照。基础容量可配置为一份；升级后的容量允许同批携带不同桌餐点，但只影响下一次取餐，不改变已经在途的批次。
- 扩容批次以已领取的主餐点为必选项，其余餐点按 Service 优先级、地面到餐桌路线成本、等待时刻和稳定 ID 选择。并入批次的旧等待任务会立即通过 Service 同步取消，避免另一名服务员重复领取。
- 配送过程保持主 Service Task 不可中断；每送达一桌后，根据当前位置重新选择最近的下一桌，不进行全局路线求解。同桌餐点逐份送达，已成功的单份会立即保存，后续失败或读档可从剩余餐点继续。
- 每份送达通过 Order 与 Inventory 的联合事务移除服务员携带的成品实例、推进为 `served`，并按实际送达服务员当时的魅力与可注入小费策略锁定小费。小费只累积到订单，仍由结账统一入账。
- 最后一份餐点送达后，模块通过 R6-05 外部交付协议完成批次主 Service Task，并广播单份送达和整批完成事件；版本化状态保存角色绑定、容量快照、剩余餐点、当前位置及已结算小费。

## R6-07：脏盘回收与餐盘补给

- 新增独立 `DishwareServiceModule`，只编排 Customer、Order、Dishware、Inventory、Service 与 Logistics 的交接，不建立第二份餐盘库存；餐盘总量、状态和唯一位置继续由 R3-06 Dishware/Inventory 权威保存。
- 已食用餐点通过稳定 `mealId -> plateId` 绑定释放原装盘餐盘：同一个餐盘实例从 `in_use` 转为桌面脏盘位置并标记 `dirty`，不会创建替代实例或直接回到橱柜。
- 清桌 Service Task 开始后保持不可中断，服务员先从对应餐桌收取全部脏盘并放入角色携带位置；餐桌在携带期间仍为脏桌，只有全部餐盘真正进入指定橱柜后才调用 Customer 恢复桌位并完成 Service Task。
- 脏盘进入橱柜后立即交给现有 Dishware 自动清洗队列。清洗并行数和耗时继续使用橱柜实例配置，不要求员工驻留；开始、完成、状态变化和清桌完成均发布领域事件。
- 餐盘补给按飞艇目标量创建稳定的单盘服务工作。每个工作预留一个具体干净餐盘，避免装盘与多个服务员重复领取；服务员将其送入地面交换站后释放服务预留，并创建绑定同一实例的 Logistics 普通补给需求。
- Service 新增可注入餐盘补给来源。日常补给基础优先级低于接待点单；厨房因缺盘阻塞订单时提升到订单阻塞层并标记紧急。已经开始的单盘交付不可中断。
- 目标量计算同时扣除飞艇现有干净盘、活动 Logistics 在途量和已创建服务工作。目标被其他来源提前满足时，只撤销未开始工作并释放具体餐盘预留；已经领取的工作继续交付，不产生隐式退货。
- 版本化存档保存已处理餐点、清桌携带/已归还餐盘和补给工作；恢复后不会重复把餐盘变脏、重复预留、重复建物流需求或重复洗盘。Demo 联合流程最终恢复飞艇两个、橱柜两个干净盘，四个唯一实例全程守恒。

## R6-08：财务结算与日结读模型

- 新增纯只读 `FinanceReportProjector`，直接从 Finance 不可变流水和日结快照派生当前日及历史日盈亏，不保存第二套收入、支出或余额计数。
- 报表固定提供期初余额、分类收入、收入合计、分类支出、支出合计、净收益、期末余额、当前余额、预留金额和可用余额；当日随流水实时变化，历史日按最新日期优先且只读。
- 分类明细只暴露发生时间、绝对金额、分类、地区、玩家可读来源名称和备注，不把内部订单 ID、采购 ID、流水 ID或结算批次 ID直接交给 UI。
- Order 继续以 `order:<orderId>` 作为唯一结算键，将菜品销售、小费和专注加成作为独立非零流水原子入账；相同订单即使换操作 ID 重试，也只返回原结算批次，不重复增加余额。
- LocalProcurement 付款时已直接写入 `ingredient-procurement` 支出；报表与订单收入使用同一个 Finance 账本，因此最终资金严格等于期初减采购等支出再加销售、小费和其他收入。
- 修正送餐小费策略边界：小费策略现在同时接收餐点成交单价快照和实际服务员魅力等级，按可配置魅力比例及货币最小单位四舍五入，并仍在送达时锁定、结账时入账。
- 现有 Finance 跨日流程继续先提交工资等强制支出，再锁定旧日快照并把旧日期末余额作为新日期初余额；日结重试由游戏日校验拒绝，恢复后报表从同一流水重建。

## R6-09：桌面与管理窗口稳定读模型

- 跨进程合同新增 desktop-world、operations、procurement 和 finance 四个稳定切片，并继续保留 R3 的 layout、inventory、characters 表现切片；IPC 与 preload 仍复用按键获取和订阅协议，不增加窗口专属业务通道。
- LegacyGameRuntimeCompatibility 成为旧 GameSnapshot 的唯一投影边界：每次旧运行时广播都会同步发布四个切片。旧总快照接口暂时保留给兼容测试、诊断和后续 R8 清理，但 renderer 不再读取或订阅它。
- DesktopWorld 只包含桌面表现所需的运行阶段、安静模式、经营表现、座位、餐厅活动、前景对白、采购到货提示和演示修订；座位尚未恢复时用 null 表示未知，桌面状态保留最近一次有效容量，避免窗口恢复中途跳回默认值。
- 桌面连接器现在只恢复并订阅 layout、inventory、characters 与 desktop-world。每个切片独立按修订号拒绝迟到数据；窗口重开可从当前投影重建场景，不需要重放业务事件或先拿一份总快照。
- Operations 保存经营概览、菜单、升级、故事与离线结算的只读表现；Procurement 保存采购状态、当前主推菜和时间；Finance 保存兼容期的余额、预留/可用额、累计支出和最近销售。采购、科技树和经营面板已按职责组合这些切片，不再从一份 gameplay 总对象取全部数据。
- 管理窗口初始化会并行恢复 Inventory、Operations、Procurement、Finance、设置、显示器和存档诊断。任一切片失败只报告该来源，其他切片仍可显示；订阅先到的新修订不会被较旧的初始化响应覆盖。
- 管理命令仍沿用现有命令 IPC，但命令返回携带的旧快照不再写入 React 状态；成功后由稳定切片广播刷新，失败后的主动恢复也只重取四个管理切片。写侧业务边界留到 R6-10 继续清理。
- renderer 源码审计已无 GameSnapshot、getSnapshot、onSnapshotChanged 或 runtimeSnapshot 业务引用；旧总快照只存在于主进程兼容接口和诊断边界。
## R6-10：删除 renderer 服务业务写入
