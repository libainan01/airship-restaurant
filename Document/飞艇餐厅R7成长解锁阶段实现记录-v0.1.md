## R7-01：Technology 模块（已完成）

### 现状审计

- 当前管理窗口仍读取旧 M2 `BusinessUpgrade`：厨房炉组、运输绞盘、餐厅扩座和采购委托。它们直接修改旧 GameplaySnapshot，不是模块化 Technology 的权威状态。
- “采购委托”通过科技开放自动采购，与已确认规则冲突：自动补货只由后续剧情关键角色担任餐厅管理员且在岗时提供，不存在自动采购科技。
- 厨房设备、等候区、橱柜、本地采购小车和采购飞艇均为具体建筑或载具实例，其容量、耐久与样式升级属于 R7-02，不进入全局 Technology；餐桌按桌型解锁，人员电梯暂不提供升级。
- Content 已有 cargo_lift_speed、cargo_lift_count、personnel_elevator_speed、recruitment_center 四个节点；其中人员电梯效率应从全局科技删除并保留独立基础配置，同时补入组织管理与托盘改良。
- R6 固定夹具中的五项零级科技方向正确，但目前只是常量，不具备付款、前置、效果查询、事件和存档能力。

### R7-01 唯一全局科技

| 节点 | 负责效果 | 不负责 |
|---|---|---|
| 货梯传动效率 | 小型货梯后续行程的移动速度/时长系数 | 单台货梯实例耐久、维修、样式 |
| 并行货梯槽位 | 可启用的小型货梯数量，基础四台之上的扩容 | 单件载货规则、交换站容量 |
| 组织管理 | 餐厅员工数量上限 | 具体角色日程、职位和工资 |
| 托盘改良 | 服务员下一次取餐批次的携带数量 | 当前已领取批次、角色移动速度 |
| 招募网络 | 下一次候选池的属性与天赋质量权重 | 剧情角色、核心成员资格、自动补货 |

### 实现边界

- TechnologyModule 负责节点定义、等级、前置校验、资金原子扣除、按 key 查询当前效果和等级变化广播；不直接修改货梯、员工、托盘或招募模块内部状态。
- 消费模块通过 Technology 效果查询端口在创建新行程、新批次或下一次刷新时读取快照；已经开始的工作保留原快照，不被中途升级改写。
- 每次升级只允许从当前等级提升一级；资金不足、前置未满足、满级和未知节点均拒绝且不产生部分扣款。
- 等级与版本化状态进入模块存档；Content 只提供稳定节点、最大等级、逐级费用、前置和效果表，不在 UI 硬编码。
- 旧 M2 `gameplay.purchase-upgrade` 仅保留兼容期入口，待 Technology 命令、稳定读模型和界面迁移后删除；不得继续扩展旧四项升级。

## R7-03：招募、雇佣与工资日结（已完成）

### 审计结论

- 当前只有 `recruitment.quality-tier` 科技效果以及 `employee-recruitment`、`recruitment-refresh` 财务分类，没有候选池、刷新周期或招募领域模块。
- Employment 已具备统一员工记录、核心成员不可解雇、延迟解雇、职位与单班次日程；R7-03 应复用它，不重复建立员工名册。
- 原 CharacterInstance 只保存定义 ID，姓名和初始技能始终来自固定定义，无法承载随机普通候选；这是建立 RecruitmentModule 前的结构前置。

### 已完成基础

- CharacterState 升级到 v2：角色实例持久化姓名，创建请求可传入候选生成后冻结的五项初始技能与最多三个天赋。
- Character 读模型改为读取实例姓名；`character.created` 广播包含实例姓名，后续 UI 与事件无需回查候选池。
- v1 角色状态自动以原角色定义姓名迁移到 v2，不改变技能进度、天赋、核心成员身份或稳定实例 ID。
- Content 已加入普通招募模板、姓名池、职位组合、四档品质曲线与通用天赋品质；生成器会排除顾客、剧情角色、专属天赋和带固定天赋的模板。
- 新增 `RecruitmentModule`：候选按刷新时点冻结姓名、技能、天赋、职位、费用和品质；支持固定周期免费刷新、同周期递增主动刷新费用与品质科技快照。
- 录用通过 Recruitment + Finance + Character + Employment 四模块事务完成；会校验非核心员工容量，任一环节失败均恢复候选池、资金、角色和员工记录。
- 定向验证覆盖候选快照、刷新费用递增与重置、资金不足回滚、成功录用和容量限制。
- Character、Employment 和 Recruitment 均提供公开结构校验器；存档层只做纯结构校验，模块恢复时继续校验角色引用、核心身份、职位和 Content 语义。
- 三者已作为独立模块接入模块化存档；Character 与 Employment 必须成对出现，Recruitment 必须依赖二者，不完整组合会在写盘前拒绝且不会令存档状态卡在 saving。
- 桌面启动按 Character → Employment → Recruitment 顺序恢复；新档自动执行首次免费刷新，旧档恢复冻结候选且不会重新抽取。
- 联合验收覆盖生成候选、原子录用、写盘、重新创建人员/招募运行时，以及姓名、技能、天赋、职位、剩余候选与刷新计数一致性。

### 实现结果

### 关键边界

- “安静模式”仍只控制环境表现与闲聊频率，不承担专注业务状态，避免显示设置和玩法状态耦合。
