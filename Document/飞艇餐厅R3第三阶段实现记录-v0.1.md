# 飞艇餐厅 R3 第三阶段实现记录 v0.1

> 完成日期：2026-08-18  
> 对应任务：R3-08  
> R3 阶段状态：已完成

> 历史阶段记录：本文描述 R3 完成时仍保留的过渡适配。相关旧聚合和总快照边界已在 R8 删除；当前实现见《飞艇餐厅当前技术架构 v0.1》。

## 1. 本阶段结果

完成 `LayoutReadModel`、`InventoryReadModel`、跨进程分片订阅和前端读取迁移。旧 `InventorySystem` 仍保留同名 API 供 M2、Cooking、Logistics、Procurement 与 Restaurant 兼容调用，但不再保存数量、预定或转移状态；所有库存写入均落到唯一的 `InventoryModule`。主进程直接用该模块发布库存读模型，不存在新旧库存双写。

## 2. 布局与库存读模型

主要实现：

- `packages/core/src/projections/layout-read-model.ts`
- `packages/core/src/projections/inventory-read-model.ts`
- `packages/core/src/projections/r3-read-model-publisher.ts`

`LayoutReadModel` 按场景输出建筑实例、位置、朝向、样式、等级、耐久、稳定组件 ID、世界占地、视觉边界、交互区和 Y 排序值；收起建筑单独投影，不携带表现层座位或会话占用。

`InventoryReadModel` 按位置统一堆叠食材、餐盘、半成品和餐点，输出总量、预定量、可用量、在途量、分类仓位、稳定实例和餐盘生命周期汇总。读模型只由 Inventory/Dishware 快照派生，不保存业务计数，也不参与命令处理。

`R3ReadModelPublisher` 为 layout 与 inventory 分别维护 revision。只有对应来源 revision 变化时才发布该切片；窗口初始化可以读取当前完整切片，不依赖历史事件回放。

## 3. 单一库存写入迁移

`packages/core/src/inventory-system.ts` 已改为 `InventoryModule` 的兼容门面：

- 旧公开方法签名与存档格式保持不变；
- 入库、出库、转移、资源预定、释放、消耗和“消耗预定并产出”全部委托给 InventoryModule；
- 复合烹饪操作使用 InventoryModule 事务会话，消耗或产出任一步失败都会回滚；
- 旧容器总容量和单物品容量仍由兼容门面做前置校验，但门面不保存数量；
- M2Simulation 暴露底层唯一 InventoryModule 给组合根作为读模型来源；
- 旧 v1 存档继续按容器堆叠恢复，再建立 InventoryModule，不要求玩家重开存档。

为保持 30 天离线推进性能，InventoryModule 增加轻量只读查询；兼容容器快照按模块 revision 缓存，库存变化后自动失效。缓存只保存可重建视图，不是业务权威状态。30 天离线推进实测约 8.7 秒，继续满足原 15 秒测试门槛，幂等历史仍保留 1024 项。

## 4. 独立 IPC 与渲染端迁移

contracts 和 preload 增加按 key 的 `getReadModel` 与 `onReadModelChanged`：

- DesktopWindow 与 ManagementWindow 分别订阅 `layout`、`inventory`；
- 主进程按 webContents 与 key 维护引用计数，只向实际订阅窗口发送变化；
- 订阅握手直接返回当前切片，解决“先读取还是先订阅”之间的竞态；
- Phaser 连接器为每个切片维护独立 revision，较旧或重复初始化结果不会覆盖新推送；
- React 管理端的经营概览与采购面板改读 InventoryReadModel；
- Phaser 的餐厅库存标签和厨房表现输入改读 InventoryReadModel；
- 前端已不再直接访问 `GameSnapshot.gameplay.inventory`。

旧总 GameSnapshot 仍作为其他未迁移模块的兼容门面，按既定 R4—R8 顺序继续收缩。

## 5. SceneLayout 组合根

`apps/desktop/src/main/r3-runtime.ts` 把已经通过 schema 校验的建筑内容目录转换为 SceneLayoutModule 运行时定义。当前存档尚没有玩家摆放建筑，因此初始布局为空；但 layout 切片来源已经是真实 SceneLayoutModule，而非临时空对象。后续建造命令只需写入该模块，不需要再次更换 Phaser 契约或 IPC 通道。

旧 Phaser `RestaurantLayoutRuntime` 中被冻结的顾客座位和会话占用属于 R4/R6 的 Customer、Movement 与 Service 迁移范围，不会写入新的 SceneLayout 或 LayoutReadModel；本阶段没有为它建立第二份状态。

## 6. 验收

本阶段新增 4 项核心/组合测试：

- LayoutReadModel 几何、组件与收起建筑投影；
- InventoryReadModel 堆叠、稳定实例、在途数量与餐盘汇总；
- layout/inventory 独立 revision 与订阅；
- 建筑内容目录到 SceneLayoutModule 的组合根映射。

同时回归旧 InventorySystem 8 项，以及 Cooking、Logistics、Procurement、Restaurant、M2 的全部既有用例。最终 `npm run check` 通过：90 个 Vitest 文件、389 个测试及 4 个 Node 测试全部通过；内容校验、依赖边界、TypeScript 严格检查和生产构建均通过。Vite 仍只有既有的 desktop 大 chunk 警告。
