# 飞艇餐厅当前技术架构 v0.1

> 文档状态：Electron 版本当前实现说明。更新日期：2026-08-24。若历史阶段记录与本文冲突，以代码、自动架构检查和本文为准。
>
> 目标路线已于 2026-08-24 调整：后续产品采用 Godot .NET 逐块重写，不再继续把本文所述 Electron、Phaser、React 技术栈扩展为最终客户端。目标架构、审核门禁与阶段顺序以《飞艇餐厅 Godot 逐块重写技术方案 v0.1》为准。旧实现保留为可运行参考，不是新实现必须复刻的行为标准。

## 1. 架构目标

项目采用“领域模块拥有事实、运行时负责组合、读模型服务界面、renderer 只负责表现”的结构。重构后的核心约束是：一类业务事实只能有一个权威写入者，不通过 UI 状态、总快照副本或兼容对象维持第二份可写状态。

游戏是 2D 平面桌面伴宠。地面、飞艇和港口是业务区域，不是物理楼层；普通桌椅、设备与装饰不阻挡角色。人员跨区域使用人员电梯，物资跨区域使用交换站和单件小型货梯。

## 2. 运行层次

```text
Electron main（组合根、时钟、存档、IPC）
        │ 命令 / 分片读模型
        ▼
Kernel + Domain Modules + GameplayRuntime
        │ 领域事件 / 投影
        ▼
RuntimeReadModelFacade
        │ 带 revision 的只读切片
        ├── Phaser Desktop（Projector / PresentationModel / Renderer）
        └── React Management（查询、命令与纯 UI 状态）
```

- Kernel 提供命令总线、领域事件总线、同步事务、Process Manager 和稳定 ID；
- 领域模块保存角色、任务、订单、厨房、库存、建筑、物流、采购、财务、成长和剧情等权威状态；
- `GameplayRuntime` 编排仍需连续推进的经营流程，但不再保存整套模块镜像，也不作为聚合存档边界；
- Electron 主进程注册模块、推进时间、处理存档，并向两个窗口发布它们订阅的切片；
- Phaser 与 React 只能发送公开命令，不能直接写领域对象。

## 3. 核心业务边界

| 边界 | 权威职责 |
|---|---|
| Character / Employment / Schedule | 统一角色对象、技能与天赋；员工身份、职位、日程和核心成员限制 |
| Task | 任务发布、候选资格、职位偏好、业务优先级、等待时间和任务生命周期 |
| Customer / Order / Service | 顾客来访、点单、订单、服务步骤、餐桌清理和等待区 |
| Recipe / Cooking | 真实菜品定义、简化配料、详细现实食谱、DAG 步骤、设备工作位和厨师快照 |
| Inventory / Storage / Dishware | 混合物品账本、预定、分类仓储、餐盘洁净循环和容量 |
| Logistics | 双交换站需求、四台单件小型货梯、优先级、租约和阻塞恢复 |
| Procurement / Fleet | 本地采购、航线采购、采购员小车、飞艇货量、航程与飞艇冷却 |
| SceneLayout / Building | 2D 布局、建筑实例、尺寸占地、编辑预览、预扣款、移动和实例升级 |
| Finance / Progression | 收支流水、日结、科技、永久解锁、建筑与载具实例升级 |
| Narrative / Relationship / Focus | 故事阶段、花名册、好感度、闲聊、剧情时间窗和番茄专注模式 |

跨模块流程通过显式端口、命令、领域事件或 Process Manager 协调。例如订单先预定食材；食谱 DAG 发布可执行步骤；任务完成统一广播；财务是铜币和流水的唯一权威；物流只处理运输需求，不直接决定厨房或餐厅状态。

## 4. 角色与任务

NPC、白夜城、奥托、剧情角色与普通员工共享角色对象。身份和当下用途由角色事实、标签、雇佣关系与日程决定：只有当前具备员工资格的角色才能领取餐厅工作，顾客不会因技能匹配突然离桌做饭。

任务选择综合硬资格、职位偏好、业务优先级、等待时间和距离。烹饪步骤由食谱 DAG 解锁，可以并行或等待多个前置步骤；步骤是否需要人员持续在场由食谱定义。已开火且无需持续在场的蒸煮或煎炒会自行推进，完成后发出通知，不设置煮糊和订单取消。

所有任务完成都发布领域事件，音效、UI、剧情和统计只能订阅结果，不能反向成为任务完成的条件。

## 5. 场景、建筑与物流

建筑由实例和能力组件组合。仓储是能力组件，按物品分类标签、容量和分区限制接收物品；地面交换站使用很高但有限的容量，以保持统一模型。建筑预览只有在资金足够时才能创建，并在预览阶段预扣款；取消归还，确认转为正式支出。

普通建筑不参与碰撞寻路。目标建筑移动后，受影响角色重新计算目标位置；进入编辑模式时游戏暂停。正在被设备工作位占用的设备不能拆除，但可以更换样式。

地面和飞艇交换站分别保存食材、餐点与餐盘分区。四台小型货梯一次只运输一个物体，只在有需求时移动。玩家可以创建指定数量的手动运输需求，每成功运输一个单位便递减一次；系统补给与餐点出餐使用同一套领取、租约、到达和完成事件。

## 6. 采购、舰队与自动补货

本地采购由采购员和小车执行，单次携带上限属于采购能力；航线采购由飞艇执行，单次货量属于飞艇实例。船长可在可用时立即出发，出行后的冷却属于飞艇，以鼓励玩家扩充舰队。

自由采购按食材创建数量，食谱采购把菜品数量展开为现实存在的食材需求；跨地域配料可以拆成多个来源和到货时间。自动补货只由剧情解锁的餐厅管理员职位提供，不在科技树中建立第二套自动采购入口。

## 7. 读模型与 UI

公开读模型 key 为：`layout`、`inventory`、`characters`、`instance-upgrades`、`recruitment`、`progression`、`desktop-world`、`operations`、`procurement`、`finance`。每个切片有独立 revision；窗口重建时按 key 读取初值，此后只订阅相关切片。

`RuntimeReadModelFacade` 只公开按 key 的读取、订阅和命令路由。命令回执不携带整套业务状态。

桌面 renderer 的 `RestaurantNpcProjector` 把角色、顾客、对话和布局切片映射为 Actor Frame；`DesktopWorldPresentationModel` 缓存表现所需的最新切片、气泡和动画 revision。二者都是只读表现对象，不保存任务、订单、顾客阶段或剧情事实。

## 8. 存档

正式存档 schema 为 v2，按功能模块保存经营状态，不保存旧的聚合模拟块。加载旧档时先在内存中迁移，不改写来源文件；第一次成功保存 v2 时保留原主档为备份，并保留未知模块。

落盘采用临时文件、同步写入、反读校验、备份和原子替换。主档损坏时尝试有效备份；主档与备份都损坏时明确拒绝旧内容且不覆盖源文件。管理窗口展示加载来源、迁移状态和诊断信息。

## 9. 架构护栏

以下规则由 `npm run check` 自动验证：

- 禁止恢复已删除的旧聚合类型、旧总快照 IPC 和旧兼容门面；
- 禁止 renderer 恢复服务任务队列、顾客业务协调器或可写 Director；
- 受保护的 Projector 与 PresentationModel 不得派发业务命令或调用任务生命周期写 API；
- 跨包只能通过公开出口导入，core 运行时依赖图必须无环；
- 当前文档不能把废止结构描述成现状，阶段文档必须明确标记为历史记录。

## 10. Electron 版本生产边界

R0—R9 已完成领域模块重构、单一生产经营世界和正式纵向验收。产品组合根只运行由 RestaurantApplicationRuntime 协调的运营领域模块；旧 GameplayRuntime、R6 Demo 和表现 Demo 不进入产品命令、读模型、存档或财务。

R10 已把剩余产品缺口接入同一世界：

- 货梯损耗由正式维修任务与员工修理能力闭环，不存在第二套维修状态；
- 剧情顾客好感度由正式到店和真实餐点消费事件驱动，闲聊不增加好感度；
- 建筑购买、预扣款、摆放、移动和样式切换通过 SceneLayout、BuildingConstruction 与唯一 Finance 完成；
- 玩家手动运输复用 LogisticsDemand 和四台单件货梯，不创建独立运输模拟；
- 仓库与食谱成为独立 UI 入口，分别读取唯一 Inventory 与内容/解锁状态；
- 音效只订阅已完成的经营事件，安静模式不回放历史事件。

在 Godot G0 开始前，Electron 版本的必要修复仍须沿用既有模块所有权、分片读模型、扩展命令链和模块化存档，不得恢复聚合运行时、renderer 业务写入或主进程内容硬编码。新的玩法实现默认进入 Godot 重写计划，不继续扩大旧表现层。

## 11. 新目标路线

新版本不做逐行移植，也不建立长期的 Godot＋Node 双运行时。其原则为：

1. 功能需求和每块新的审核结论高于旧代码行为；
2. Godot 场景负责可视结构，点击区、锚点、动画、光照和 UI 均可在编辑器中预览；
3. C# 领域层继续保持表现无关、单一事实所有权、确定性推进和模块化存档；
4. 旧 Electron 应用与新 Godot 应用在迁移期并存，但不共享可写状态、不双写存档；
5. 每块先提供可运行样板，经用户审核通过后才冻结规则并进入下一块；
6. 旧玩家正式存档在方案未单独批准前不得由 Godot 项目读取或修改。
