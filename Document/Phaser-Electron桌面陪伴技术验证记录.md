# Phaser + Electron 桌面陪伴技术验证记录

记录日期：2026-07-28

## 1. 验证目的

《空艇餐厅》的核心体验是“陪伴感”：游戏世界应该能够让玩家桌面持续保持活力，
同时不妨碍 Word、浏览器、聊天工具和开发软件的正常操作。

本次验证不评估正式经营玩法，只验证以下技术前提：

1. 游戏画面能否以透明、不连续的形式分布在桌面上。
2. 中央角色和视觉效果能否保持可见，同时把点击交给后方应用。
3. 顶部厨房、底部餐厅和临时任务气泡能否独立恢复交互。
4. 动态交互区能否随游戏状态增加和撤销。
5. 点击游戏内容时，Electron 是否会抢走玩家的键盘焦点。
6. 透明桌面客户端的初步 CPU、内存和构建体积是否可接受。

## 2. 验证环境

- 操作系统：Windows 10/11 x64
- 显示区域：2560 × 1392 工作区
- Electron：43.2.0
- Chromium：由 Electron 43.2.0 内置
- Phaser：4.2.1
- TypeScript：7.0.2
- Vite：8.1.5
- Node.js：22.14.0
- 渲染帧率目标：30 FPS

## 3. 验证实现

验证项目位于：

`spikes/phaser-electron`

采用单个覆盖显示器工作区的透明 Electron 窗口：

- `frame: false`
- `transparent: true`
- `backgroundColor: #00000000`
- `alwaysOnTop: true`
- `focusable: false`
- `skipTaskbar: true`
- `backgroundThrottling: false`

Phaser 使用透明 Canvas 绘制：

- 顶部飞艇厨房；
- 底部餐厅；
- 中央运输飞艇和陪伴角色；
- 云雾和蒸汽；
- 右侧缆车；
- 临时食谱气泡。

视觉系统与输入系统分离。视觉对象可以任意分布，输入由独立
`SemanticHitMap` 决定。

当前语义交互区包括：

- 顶部厨房带；
- 底部餐厅带；
- 顶部控制按钮；
- 底部交互测试按钮；
- 出现期间的食谱气泡。

中央运输艇、陪伴角色、云雾和缆车轨道不加入命中地图，因此保持可见但穿透。

Electron 主进程每 33 毫秒读取一次系统光标位置，将窗口坐标发送给渲染进程。
渲染进程根据命中地图返回当前是否需要交互：

- 命中交互区：`setIgnoreMouseEvents(false)`
- 未命中交互区：`setIgnoreMouseEvents(true, { forward: true })`

## 4. 验证结果

### 4.1 透明渲染

通过。

Electron 截图尺寸为 2560 × 1392，格式为 32 位 ARGB。
中央空白位置实测像素为：

`ARGB = 0, 0, 0, 0`

说明中央黑色只是在普通图片查看器中用于表示透明背景，窗口实际 Alpha 为零。

### 4.2 不连续画面

通过。

顶部厨房、底部餐厅、中央角色、运输飞艇、云和缆车能够同时显示，
视觉元素之间不要求形成连续多边形。

### 4.3 固定交互区

通过。

使用 Windows 原生 `WindowFromPoint` 验证顶部区域，返回的窗口进程为本验证项目的
Electron 进程。

### 4.4 可见角色位置穿透

通过。

在中央陪伴角色的可见位置执行 `WindowFromPoint`，返回后方的企业微信窗口，
而不是 Electron。说明“角色可见，但点击后方应用”在实际 Windows 窗口层成立。

### 4.5 临时食谱气泡

通过。

食谱气泡出现后，同一位置的 `WindowFromPoint` 返回 Electron；
气泡被点击并隐藏后，该位置重新恢复桌面穿透。

最终输入状态日志：

```text
recipe-bubble
input-lock
desktop
```

### 4.6 键盘焦点

通过，但需要保持输入锁。

最终自动点击验证中：

- 点击前的前台应用为 Unreal Editor；
- 点击食谱气泡后，前台应用仍为 Unreal Editor；
- Electron 没有成为前台应用。

这证明当前非激活窗口配置不会抢走玩家正在使用的软件的键盘焦点。

### 4.7 命中地图测试

通过。

Vitest 共执行 4 项测试：

1. 上下不连续交互岛互不干扰；
2. 临时圆形食谱气泡可以增加和删除；
3. 按钮优先于其所在的固定交互带；
4. 禁用区域不会被命中。

### 4.8 TypeScript 和生产构建

通过。

- 严格 TypeScript 检查无错误；
- Vite 生产构建成功；
- 主 JavaScript 包约 1.386 MB；
- Gzip 后约 362 KB。

Vite 提示单个 Chunk 超过 500 KB。主要来源是 Phaser 本体，
技术验证阶段可以接受，正式项目应评估代码拆分和调试功能隔离。

## 5. 初步资源数据

在本机以 30 FPS 运行、持续绘制透明桌面场景时，Electron 启动 5 个相关进程：

- Browser
- GPU
- Tab
- Utility × 2

连续三次稳定采样的总工作集约为：

- 386 MB
- 388 MB
- 389 MB

稳定阶段采样 CPU 合计约为 0.5%～0.6%。

截图瞬间 GPU 和 Browser 工作集会短时上升，因此资源结论应以截图前的稳定采样为准。

这些数据只代表当前机器和程序绘制占位场景，不能代替正式游戏的长期性能预算。
相比 Godot，Electron 的基础内存成本明显更高；但当前 CPU 占用较低，
对于桌面挂机游戏仍具备继续验证的价值。

建议正式性能目标：

- 默认 30 FPS；
- 安静模式降至 15～20 FPS 或减少动画更新；
- 静态状态停止不必要的 Tween、粒子和布局计算；
- 避免每帧 IPC，只在交互状态改变时切换窗口穿透；
- 对故事面板和复杂 UI 使用按需加载；
- 进行至少 2 小时和 8 小时的内存稳定性测试。

## 6. 验证过程中发现的问题

### 6.1 CSS 的 `pointer-events: none` 不等于桌面穿透

CSS 只能让事件穿过网页元素，不能把事件交给其他 Windows 应用。
真正的桌面穿透必须由 Electron 主进程调用原生窗口接口。

### 6.2 `setIgnoreMouseEvents` 控制整个窗口

Electron 没有直接接收任意多边形命中地图。
本项目利用“鼠标同时只有一个位置”的事实，根据当前光标位置动态切换整个窗口。

玩家体验接近局部穿透，但实现上必须保证：

- 光标位置和 Canvas 坐标一致；
- 只在状态变化时调用窗口接口；
- 快速移动时没有明显延迟；
- 动态对象经过静止光标时也会重新计算。

### 6.3 按下后不能立刻撤销热区

第一版在食谱气泡 `pointerdown` 后立即隐藏气泡并恢复穿透，
导致同一次操作的 `pointerup` 有可能落到后方应用。

修正方式是加入输入锁：

1. `pointerdown` 时锁定窗口为交互状态；
2. 游戏可以立即更新视觉和业务状态；
3. 收到 `pointerup` 后解除输入锁；
4. 再根据当前光标位置恢复交互或穿透。

所有拖拽、长按、滑块和物资搬运都必须沿用这个规则。

### 6.4 DPI 坐标必须明确区分

Electron `screen` 使用 DIP 坐标，Windows 原生 API 和截图可能使用物理像素。

自动验证改为：

1. Phaser 上报本地语义测试点；
2. Electron 加上窗口位置形成全局 DIP；
3. 使用 `screen.dipToScreenPoint` 转换为物理坐标；
4. Windows 测试脚本再移动光标并执行命中验证。

正式项目必须统一所有命中地图、显示器工作区和存档中的坐标语义。

### 6.5 非激活窗口不适合直接输入文字

`focusable: false` 可以避免抢走玩家键盘焦点，但游戏无法直接承载需要键盘输入的界面。

如果以后需要输入餐厅名称、搜索食谱或输入数量，应选择一种明确策略：

- 临时将主窗口设为可聚焦，关闭面板后恢复；
- 打开一个独立、普通的设置窗口；
- 尽量改为按钮、步进器和预设选项。

### 6.6 自动化环境应直接运行 Electron 可执行文件

在当前 Codex PowerShell 环境中，通过 `electron.cmd` 启动曾出现父进程等待超时；
直接运行 `node_modules/electron/dist/electron.exe` 能够可靠完成烟雾测试和自动退出。

这属于开发自动化差异，不影响玩家最终安装包。

## 7. 技术结论

本次验证确认 Phaser + Electron 能够实现《空艇餐厅》最关键的桌面陪伴体验：

- 可视内容不需要连续；
- 视觉内容可以覆盖桌面任意位置；
- 非交互角色和效果能够保持可见并穿透点击；
- 固定建筑和临时任务能够独立恢复交互；
- 游戏不会默认抢走玩家键盘焦点；
- 语义交互区可以随剧情和游戏状态动态变化。

建议将 Phaser + Electron 作为新的客户端技术方向继续推进。

Godot M0 应保留为对照和设计验证，不立即删除。它已经验证了任务栏避让、
窗口置顶、多显示器布局和首次启动设置，这些产品决策仍然有效。

## 8. 进入正式开发前仍需验证

1. Windows 10 与 Windows 11 的不同缩放比例和多显示器组合。
2. 任务栏位于顶部、左侧或右侧时的工作区布局。
3. 睡眠、锁屏、远程桌面和显示器热插拔后的窗口恢复。
4. 2 小时与 8 小时常驻运行的内存变化。
5. 大量 Sprite、粒子、骨骼动画和剧情 UI 下的 CPU/GPU 表现。
6. Steam Overlay、截图、录屏和不同全屏应用的兼容性。
7. 安装包、自动更新、崩溃恢复和单实例运行。
8. 键盘输入面板采用临时聚焦还是独立普通窗口。

## 9. 已确认的桌面空间与交互规则

桌面层继续采用“视觉分布”和“输入分布”相互独立的原则。Electron 透明窗口覆盖目标显示器工作区，但只有加入 `SemanticHitMap` 的对象接收点击。对象是否可见、是否透明、是否播放动画，均不能自动决定它是否可交互。

### 9.1 顶部飞艇厨房

- 飞艇悬浮在视口顶部，外观可以是不规则轮廓。
- 只有飞艇船体和明确设计为可操作的部件接收点击。
- 飞艇轮廓之外的透明区域完全穿透，不使用整条顶部矩形作为最终交互区。
- 正式资源接入后，由组件上报矩形、圆形或多边形语义热区；不得依赖 Sprite 的包围盒直接扩大点击范围。

### 9.2 屏幕边缘缆车

- 缆车沿屏幕边缘在飞艇厨房、底部餐厅和未来港口之间运输物资。
- 缆车及其轨道属于纯视觉和状态反馈，不加入命中地图。
- 缆车经过鼠标所在位置时也必须保持桌面穿透。
- 如未来需要查看货物详情，应通过厨房、餐厅或港口的固定入口打开，而不是让高速移动的缆车成为点击目标。

### 9.3 中后期港口

- 港口建立在屏幕边缘，只让港口建筑及明确的操作部件接收点击。
- 停靠飞艇、装卸动画、蒸汽、灯光和其他越出港口轮廓的效果默认只显示、不接收点击。
- 贸易、故事和战场捐赠均通过港口入口进入；港口作为交易场所的业务职责不由桌面命中系统承担。

### 9.4 底部餐厅

- 餐厅位于屏幕底部，使用贯穿单个目标显示器宽度的矩形区域。
- 餐厅高度暂未确定，后续依据角色可读性、订单信息密度和桌面遮挡程度共同验证。
- 餐厅矩形可以作为稳定交互带；向上弹出的临时界面必须在出现时注册热区，关闭后撤销。

### 9.5 其他桌面视觉内容

角色、飞鸟、云层、天气、运输艇、烟雾、节日装饰和环境特效默认采用“可见但不可点击”策略。只有明确承担玩家操作的对象才进入命中地图。这样可以增加桌面热闹程度和陪伴感，同时避免大量移动对象截断玩家对后方软件的操作。

## 10. 二级界面与管理窗口方案

科技树、设置、角色档案和故事图鉴等界面信息密度高、停留时间长，并可能需要键盘焦点。这些界面不应强行塞入常驻透明桌面窗口。客户端采用分层界面架构：

| 界面层级 | 典型内容 | 实现位置 | 输入与焦点策略 |
| --- | --- | --- | --- |
| 临时轻量界面 | 食谱气泡、订单详情、短对话、Toast | Phaser 桌面窗口 | 动态注册语义热区；关闭后立即恢复穿透 |
| 中型经营面板 | 背包、菜单、生产队列、港口报价 | 桌面窗口内的 DOM/Phaser 面板，或从餐厅区域展开 | 只扩大面板实际占用区域；避免全屏透明控件拦截输入 |
| 深层管理界面 | 科技树、设置、角色档案、故事图鉴 | 独立普通 Electron `BrowserWindow` | 不透明、可聚焦、可调整大小，可最小化和关闭 |
| 阻塞式确认 | 删除存档、重置进度、不可逆重大选择 | 管理窗口的模态子窗口或内部对话框 | 仅在确实必须阻止继续操作时使用 |

### 10.1 窗口职责

桌面陪伴窗口继续负责 Phaser 世界、透明渲染、语义命中地图和低打扰动画。它默认无边框、不可聚焦，并按玩家设置决定是否置顶。

管理窗口采用普通不透明网页窗口，负责科技树、设置和其他复杂信息架构。该窗口应在玩家主动点击入口后获得焦点；默认不始终置顶，不采用模态模式阻塞桌面工作。窗口可由桌面窗口创建，但是否设置 Electron `parent` 关系，需要在正式实现时验证置顶层级、任务栏表现和多显示器行为后决定。

科技树可以由飞艇上的工程台、蓝图桌或其他世界内入口打开。打开管理窗口时，桌面世界继续运行，不因二级界面存在而扩大桌面窗口的交互区域。

### 10.2 科技树技术选型

科技树管理窗口建议使用 React 和 `@xyflow/react`（React Flow），不使用 Phaser 从头实现复杂节点编辑与视口操作。

React Flow 负责：

- 科技节点、连接线和前置依赖关系；
- 画布拖动、缩放、自动适配视野；
- 小地图、缩放控件和背景网格；
- 节点选择、禁用、锁定和解锁状态样式；
- 自定义节点组件。

自定义科技节点可展示图标、名称、费用、前置条件、可购买原因、解锁状态和悬停说明。节点的美术表现可以设计成机械蓝图、铜管、铆钉和锅炉结构，但依赖关系和购买规则仍由 `ProgressionSystem` 管理，React Flow 只负责展示与操作。

首选参考：

- Electron `BrowserWindow`：https://www.electronjs.org/docs/latest/api/browser-window
- React Flow 自定义节点：https://reactflow.dev/learn/customization/custom-nodes
- React Flow 视口与平移缩放：https://reactflow.dev/learn/concepts/the-viewport
- React Flow 内置组件：https://reactflow.dev/learn/concepts/built-in-components

### 10.3 进程与状态同步

正式客户端建议形成以下边界：

```text
Electron 主进程
├─ 桌面陪伴 BrowserWindow
│  └─ Phaser：飞艇、餐厅、港口、角色、缆车和环境效果
├─ 管理 BrowserWindow
│  └─ React：科技树、设置、档案和图鉴
└─ 游戏状态／持久化服务
   └─ 校验命令、更新状态、保存并向两个窗口广播事实事件
```

两个渲染窗口不得各自维护一份可独立修改的核心游戏状态。建议使用类型化 IPC：

1. 管理窗口请求当前只读状态快照；
2. 玩家点击升级后提交 `purchase-upgrade` 等业务命令；
3. 游戏状态层统一校验货币、材料和前置条件；
4. 命令成功后广播 `upgrade-purchased`、`effect-changed` 等事实事件；
5. React 科技树和 Phaser 桌面表现分别刷新。

Electron 渲染进程继续启用上下文隔离，通过最小化的 preload API 暴露白名单命令，不向页面直接开放完整 Node.js 或任意 IPC 能力。

### 10.4 窗口生命周期

- 第一次打开时创建管理窗口，后续优先复用，减少重复初始化成本。
- 玩家主动打开管理界面时允许窗口正常获得焦点。
- 关闭或隐藏管理窗口后，不自动把焦点抢回桌面陪伴窗口。
- 桌面模拟和现实时间任务继续运行；管理窗口隐藏时停止不必要的 React 渲染。
- 设置窗口与科技树可以共享管理窗口外壳，通过路由进入不同页面。
- 科技树属于非模态管理界面；普通游玩过程中不得强迫玩家立即处理。

### 10.5 正式开发前验证项

1. 透明置顶窗口与普通管理窗口同时存在时的前后层级。
2. 从不可聚焦桌面窗口打开可聚焦管理窗口时的焦点切换。
3. 管理窗口在多显示器和不同 DPI 下的初始位置、记忆与越界恢复。
4. 管理窗口关闭、隐藏、崩溃或刷新时是否影响桌面模拟。
5. React Flow 在正式科技节点数量和美术资源下的性能。
6. 设置窗口修改置顶、安静模式和缩放后，桌面窗口能否即时安全应用。

### 10.6 当前架构决策

- 临时小界面保留在桌面透明窗口中，通过动态命中地图控制交互。
- 科技树、设置、档案和图鉴使用独立普通 Electron 窗口。
- 科技树首选 React Flow，Phaser 不承担复杂节点图 UI。
- 管理窗口默认非模态、非始终置顶，只在玩家主动打开时获取焦点。
- 所有窗口共享同一业务事实源，通过类型化 IPC 提交命令和同步结果。

## 11. 下一轮游戏细节讨论清单

技术验证完成后，建议按以下顺序讨论游戏本身：

1. 底部餐厅的具体高度，以及顶部飞艇和边缘港口的最终美术占用范围。
2. 陪伴内容清单：角色、飞鸟、云、运输艇、维修、天气和节日事件。
3. 哪些对象只显示，哪些对象可点击，哪些对象只在特定状态下可点击。
4. 工作模式、安静模式和活跃模式的动作频率与提示强度。
5. 做饭循环：选菜、备料、烹饪、装盘、运输和售卖。
6. 食谱作为情感载体时，如何触发回忆、角色故事和剧情节点。
7. 餐厅客人、港口商船、战场捐赠和现实时间之间的关系。
8. 离线期间只结算资源、不播放故事的具体规则。
9. 玩家第一次看到游戏时，应该在几分钟内经历哪些内容。
10. M1 最小可玩版本需要保留的角色、食谱、事件和经营目标。
