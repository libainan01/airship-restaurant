# M3 首轮剧情与桌面场景表现实现记录 v0.1

更新日期：2026-07-31

状态：首轮纵向切片已实现并通过自动测试、正式构建和 Electron 实机检查

## 1. 本批次完成内容

本批次把原先分散的经营、对白和餐厅占位表现接成一条可运行的首次故事流程：

1. 云灶号抵达灰羽航标塔，白夜城与奥托用头顶气泡交谈；
2. 玩家在线完成第一笔普通售卖后，玛莎与白夜城重逢；
3. 玛莎讲出战时愿望，建立两份《贝尔家的炉火炖菜》故事订单；
4. 玩家选择该食谱并在线售出两份后，奥托送餐、客人进餐并播放第一次上桌对白；
5. 食谱日志从“尚未发现”变为“玛莎的战时愿望”，最终收录为《贝尔家的炉火炖菜》；
6. 巡线员留下新愿望，贝尔夫妇道别，完成首轮单元剧。

## 2. 运行时边界

- `StorySequenceSystem` 是可配置的阶段调度器，不直接依赖 Electron、Phaser 或 React；
- 经营模拟把本帧真实发生的 `customer.arrived`、`order.requested`、`order.confirmed`、`kitchen.notification-sent`、`kitchen.order-received`、`order.fulfilled`、`customer.left` 事件作为 `restaurantActivity` 快照交给桌面表现层；NPC 不再通过“最近一笔销量”猜测客人和订单的对应关系；
- 阶段触发支持会话开始、在线销量、前一阶段完成、选择指定食谱和故事订单完成；
- 故事订单只读取 `GameRuntime.tick()` 传入的在线经营增量；应用启动时先完成离线经营结算，再建立故事系统；
- 离线累计销量不会被补算为故事订单，也不会自动跳过对白；
- 当前对白行、已完成阶段、线上普通销量和故事订单进度写入现有本地存档；旧存档没有 `story` 字段时按新游戏故事进度初始化；
- 恢复时从保存的对白行重新开始计时，不用离线经过的墙钟时间跳行；
- 正式剧情、演示对白、普通闲聊的显示优先级依次为“演示 > 正式剧情 > 普通闲聊”。被遮挡的普通闲聊只推进已有内容，不在正式剧情期间抢占气泡。

## 3. 餐厅与角色表现

- 白夜城、奥托和客人都是独立 NPC 实例；白夜城拥有白发、胡须、围裙轮廓，奥托保持黄铜机械外观，客人继续使用不同服装色；
- 角色移动采用舒缓节奏：客人与白夜城的屏幕比例速度由每秒 0.23 降至 0.16，奥托由 0.27 降至 0.19；奥托仍略快于普通角色，三类角色的步频与身体起伏同步放慢；
- 正式说话人会稳定绑定到 NPC 实例，玛莎、托马斯和巡线员在连续对白之间不会随机换人；
- 对话参与者先申请编队位置并步行靠近，到位后才显示头顶气泡；中心桌已有客人时会作为可见旁听者加入，避免位置冲突和闪现；
- 客人实例默认在场外等待，只有收到真实到店事件或手动演示指令才会从入口出现；进店路线依次经过入口、纵向通道、桌边通道和座位，不再从场外闪现到桌边；
- 客人的经营状态严格按“进店 → 入座 → 在座 Idle → 招呼奥托 → 确认点单 → 通知厨房 → 等餐 → 用餐 → 沿通道离店 → 场外”推进；桌面上的菜品只在进入用餐状态后显示；
- 在座 Idle 会循环表现看菜单、发呆，并在存在合适邻座时尝试闲聊；这些行为可被正式点单、剧情对白或离店流程中断；
- 「到店」上下文的普通对白会把第一位客人绑定到当次真实 `customerId`，其余参与者登记为同桌同行者；对白结束后整桌回到座位，等待真实点单、上菜和用餐完成后一起离场，不再作为临时演员直接退场；
- 正式经营配置保留至少 24 秒的在座决策期，覆盖当前最长 15 秒到店对白以及进店、回座时间，避免对白还未说完时后台订单已经完成；
- 点单确认与送餐是奥托的两类独立任务，均绑定 `customerId` 和目标 NPC 实例；厨房通知通过可替换的 `KitchenOrderNotificationChannel` 调度，当前以固定延迟信号和飞艇接收灯作为占位；
- 新存档厨房在首张订单送达前保持待命；收到订单后白夜城才进入烹饪动作并启动真实制作，后续是否连续制作仍由自动续做设置决定；
- 经营订单通过 `customerId` 稳定绑定到具体客人实例；同一模拟帧内连续发生到店和成交时，送餐任务会等待对应客人完成落座和点单后才启动；没有真实送达或手动送餐演示时，客人不会进入进餐状态；
- 满座时，新客人保留在场外等待座位；若其经营来访已在等待期间结束，立即取消排队并解除实例绑定，之后不会自行重新进店；客人吃完并走完整段离店路线后同样保持在场外，直到下一次新来访；
- 奥托正在送餐时不会被对白强制打断；每个送餐任务携带目标客人实例，送达后只让该订单对应的客人进入进餐状态；
- 桌子增加椅子、餐盘、食物和蒸汽；最近一笔真实售卖会短暂显示“订单确认”和铜币反馈，奥托送餐时会高亮目标桌位；
- 角色占位整体放大，头顶气泡仍不进入点击命中地图；
- 飞艇厨房增加炉灶、炉火和悬挂锅具，保留白夜城做饭的连续动作。

## 4. 管理窗口演示模式

管理窗口新增无副作用的场景演示区：

- 强制送餐：只增加表现层送餐修订，不增减库存、销量或铜币；
- 客人进店：复用现有客人实例和座位预约，让客人从入口走到空出的座位；
- 重逢对白：播放玛莎与白夜城的正式对白内容，但不修改正式剧情阶段；
- 奥托倾听：播放单人普通台词，并让奥托走到客人身边作为倾听者；
- 显示布局点：显示座位、对话编队和功能锚点，便于后续更换美术后校准站位；
- 结束演示：清除演示对白和布局标记。

演示状态不写入存档，重启后自动清除。

## 5. 常驻性能治理

桌面渲染帧率与权威经营模拟已经解耦。经营模拟仍由主进程按现实 UTC 时间推进，表现层根据状态调整帧率：

| 状态 | 帧率上限 |
| --- | ---: |
| 正常模式，窗口可见 | 30 FPS |
| 低动态模式，窗口可见 | 15 FPS |
| 安静模式，窗口可见 | 5 FPS |
| 页面不可见／窗口最小化 | 2 FPS |

窗口失焦或长时间没有鼠标交互时不再自动降帧：桌面挂机玩家可能直接看向角色而不先与窗口交互，可见状态必须持续保持所选模式的稳定帧率。只有页面真正不可见时才使用 2 FPS；帧率变化只影响 Phaser 表现，不改变做饭、运输、售卖、离线收益和故事条件精度。

2026-07-31 实机抽样：剧情对白活跃状态下，项目 5 个 Electron 进程合计私有内存约 486 MB，10 秒平均 CPU 约为单核 1.88%，句柄约 2621。该数据只作为本机开发基线，不替代 2 小时／8 小时常驻、Windows 10 和多显示器矩阵。
