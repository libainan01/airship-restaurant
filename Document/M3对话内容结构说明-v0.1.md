# 空艇餐厅 M3 对话内容结构说明 v0.1

更新日期：2026-07-30

状态：章节 JSON、交互式创建工具、校验与生成流程已接入

## 1. 当前目标

对白内容以按章节组织的 JSON 为唯一来源。编剧／策划无需直接修改 TypeScript；
构建前由工具校验 JSON，再生成游戏可以直接读取的类型安全数据。

当前工具是终端中的交互式向导，不是可视化编辑器。它先解决以下问题：

- 新增对白时不用手写本地化键和 TypeScript 结构；
- 说话人、地点、上下文和熟悉度具有统一格式；
- 不同章节保存在独立 JSON 文件中；
- 重复 ID、未知说话人、未知地点、空文本和错误数值能被提前发现；
- JSON 改动后若忘记重新生成，构建检查会明确报错。

## 2. 文件结构

```text
packages/content/
├─ data/dialogues/
│  ├─ catalog.json
│  ├─ chapters/
│  │  └─ m3-greyfeather.json
│  └─ schemas/
│     ├─ dialogue-catalog.schema.json
│     └─ dialogue-chapter.schema.json
└─ src/m3-dialogue/
   ├─ index.ts
   ├─ dialogue-definition-builder.ts
   ├─ dialogue-json-content.ts
   └─ generated-dialogue-source.ts

scripts/
├─ dialogue-content-tool.mjs
├─ dialogue-content-tool-lib.mjs
└─ dialogue-content-tool.test.mjs
```

- `catalog.json`：地点和说话人目录；
- `chapters/*.json`：按章节保存普通闲聊与关键剧情对白；
- `schemas/*.json`：为编辑器提供 JSON 字段提示和基础格式检查；
- `dialogue-json-content.ts`：把生成数据转换成游戏内容定义；
- `generated-dialogue-source.ts`：自动生成，禁止手动编辑；
- `m3-dialogue-content.ts`：继续作为兼容入口，其他系统无需改变导入路径。

## 3. 最方便的新增方式

在项目根目录运行：

```powershell
npm run dialogue:new
```

向导会依次要求：

1. 选择章节；
2. 选择普通闲聊或关键剧情；
3. 输入稳定 ID；
4. 普通闲聊选择触发场景和最低熟悉度；
5. 从现有说话人目录中选择人物；
6. 逐句输入对白；
7. 自动校验、保存章节 JSON 并重新生成游戏数据。

新增章节：

```powershell
npm run dialogue:new-chapter
```

新增说话人：

```powershell
npm run dialogue:new-speaker
```

新增地点：

```powershell
npm run dialogue:new-location
```

这些命令都会在写入前进行完整校验，成功后自动更新生成文件。

## 4. 手动编辑 JSON

也可以直接编辑 `data/dialogues/chapters/*.json`。编辑后依次运行：

```powershell
npm run dialogue:validate
npm run dialogue:generate
```

只检查 JSON 与生成文件是否同步：

```powershell
npm run dialogue:check
```

完整项目检查也会自动执行同步检查：

```powershell
npm run check
```

如果 JSON 已变化但没有重新生成，`typecheck`、`test` 或 `build` 会提示运行
`npm run dialogue:generate`。

## 5. 章节 JSON 结构

每个章节具有自己的标题、地点和默认播放参数：

```json
{
  "$schema": "../schemas/dialogue-chapter.schema.json",
  "schemaVersion": 1,
  "chapterId": "chapter.m3.greyfeather",
  "title": "M3 灰羽航标塔",
  "locationId": "location.greyfeather_beacon",
  "defaults": {
    "lineDurationMs": 5000,
    "ambientWeight": 100,
    "ambientCooldownMs": 600000,
    "ambientMaxPlaysPerSession": 1
  },
  "ambientDialogues": [],
  "storyDialogues": []
}
```

单条普通闲聊示例：

```json
{
  "id": "dialogue.ambient.d001_cold_wind",
  "contexts": ["waiting"],
  "minimumFamiliarity": "new",
  "lines": [
    {
      "speakerId": "speaker.courier",
      "text": "先来碗热汤。风快把耳朵刮走了。"
    }
  ]
}
```

对话可以按需覆盖章节默认值：

```json
{
  "id": "dialogue.ambient.example",
  "contexts": ["arrival"],
  "minimumFamiliarity": "returning",
  "weight": 150,
  "cooldownMs": 300000,
  "maxPlaysPerSession": 2,
  "lines": [
    {
      "speakerId": "speaker.courier",
      "text": "我又来了。",
      "durationMs": 3500
    }
  ]
}
```

## 6. 当前第一层分类：运行时用途

### 6.1 普通闲聊 `ambient`

普通闲聊用于制造餐厅正在生活的感觉。它不进入重要剧情存档，不在离线期间播放，
也不会在玩家下次上线后逐条补发。

运行时会按以下字段筛选：

| 字段 | 当前作用 |
|---|---|
| `locationId` | 由章节决定对白所属地点 |
| `contexts` | 限定抵达、等待、用餐或离开等营业时机 |
| `minimumFamiliarity` | 限定新客、回头客或熟客阶段 |
| `prerequisiteEventIds` | 要求某些关键剧情已经完成 |
| `weight` | 多组对白同时满足条件时的抽取权重 |
| `cooldownMs` | 同一组对白再次出现前的冷却 |
| `maxPlaysPerSession` | 单次启动期间最多播放次数 |

当前 `contexts` 包含：

- `arrival`：出现新的在店客人；
- `waiting`：客人仍在等待；
- `eating`：刚刚完成一次售卖；
- `departing`：有客人离开；
- `idle`：类型已预留，但当前运行时不会自动生成该场景。

当前熟悉度只是 Demo 代理规则：

- `new`：累计售卖少于 5 份；
- `returning`：累计售卖达到 5 份；
- `regular`：累计售卖达到 15 份。

它反映的是整体经营进度，并不是某一位具体客人的真实好感度。以后建立客人身份和
关系系统时，需要替换这条代理规则。

### 6.2 关键剧情对白 `story`

关键剧情对白用于主线、单元剧、故事订单、食谱意义变化和重要人物关系。它目前只
保存有顺序的说话人与文本，不自行决定何时播放。

关键剧情仍需要后续剧情阶段调度器处理开始条件、玩家选择、中断恢复、回看和剧情
状态变化。把对白加入 `storyDialogues` 只代表内容已登记并通过校验，不代表它会自动
在游戏中出现。

## 7. 暂时没有固定的文学标签

当前系统没有强制划分幽默、温情、世界观、人物塑造、关系推进、战争余波或纯气氛。
这些属性可能重叠，等实际检索需求明确后，更适合增加可多选的 `tags` 字段。

章节目录负责物理组织，运行时类型负责播放逻辑，未来的文学标签负责搜索和编排。
三者彼此独立，因此以后增加分类不会改变已经进入存档的稳定对白 ID。

## 8. 后续扩展原则

- 新地区建立新的章节 JSON，不继续扩大灰羽航标塔文件；
- 一个单元剧过长时，可以拆成多个属于同一地点的章节；
- JSON Schema 和命令行校验继续保持一致；
- 独立可视化编辑器未来读写同一套 JSON，不重新设计一套私有格式；
- `generated-dialogue-source.ts` 永远由工具生成，不接受人工修改。
