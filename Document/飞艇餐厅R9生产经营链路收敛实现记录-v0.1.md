## R9-02：通用 RestaurantApplicationRuntime（已完成）

### 运行时职责

- 新增 `runtime/restaurant-application-runtime.ts`，作为正式餐厅流程协调器的确定性宿主。
- 运行时按 process ID 稳定排序，并在同一目标时间反复执行所有流程协调器，直到整张领域流程图没有新变化。
- 每次同步生成唯一 cycle、round 和 operationId；同一时间发生外部命令后可以再次同步，不会复用前一次操作 ID。
- 汇总各流程的 `nextTransitionUtcMs`，为后续离散事件推进和离线计算提供统一的下一事件边界。
- 系统时钟回拨时不调用领域流程，只返回 `clockRollbackDetected`；非法时间、重复进程 ID、非法流程结果和不收敛流程均明确拒绝。
- 运行时只保存当前协调时间、revision、cycle 和流程调度摘要，不保存订单、库存、任务、角色或财务镜像。

### 验收

- 5 项定向测试覆盖跨进程多轮收敛、稳定顺序、同时间再次同步、时钟回拨、重复 ID、非收敛和非法结果。
- core 类型检查通过。
- 架构边界检查通过：无跨包深层导入、受控出口或运行时循环依赖问题。

## R9-04：正式服务、餐盘和跨区物流（已完成）

### 正式经营闭环

- `RestaurantMealLogisticsProcess` 将装盘餐点以正式 `finished-meal` 所有者类型发布为标准 `LogisticsDemand`；四台单件货梯继续复用既有空程、装载、下送和卸载状态机。
- `RestaurantServiceWorkProcess` 贯通接待、NPC 选菜、桌边记录、一桌一提交、厨房通知、托盘取餐、逐桌上菜、用餐、结账和离店。
- 桌边点单会把最终订单编号和价格快照保存在 Service 工作流中；服务员到达固定提交点后才创建正式订单。该字段对旧存档可缺省并在读取时归一为 `null`，不改变 Service schema 版本。
- `TrayDeliveryModule.getNextTableId` 暴露当前托盘真正的下一桌，移动目标与领域模块的送餐顺序保持一致，多桌托盘不会走向错误桌位。
- `RestaurantDishwareWorkProcess` 贯通消费后餐盘变脏、桌边取盘、送回橱柜、并行洗盘、净盘补给和货梯运输；净盘补给增加持久化的 `carried-by-service` 阶段，物品先进入服务员携带容器，再在地面交换站交给物流。
- `RestaurantPersonnelElevatorProcess` 推进排队、登梯、载人和下梯，并在完成事件后调用 `Movement.completeAreaTransfer` 更新角色导航区域。
- 修正 `KitchenProduct` 与 `Inventory` 的位置双写：餐点当前位置由 Inventory 唯一负责，KitchenProduct 读模型动态投影。
- Service 内部长链路子操作 ID 使用短哈希，动态任务 ID 不再突破领域限制。

### 实际场景移动

- 新增可复用的 `RestaurantServiceMovementGate`，把“任务已认领”和“角色已抵达”明确分开；业务动作只能在 Movement 抵达建筑交互区后执行。
- 移动策略把逻辑桌位、订单提交点、地面取餐点、橱柜和餐盘交接点映射为实际场景目标；交互位在阶段完成后必定释放。
- 服务流程会计算移动抵达时间并上报 `nextTransitionUtcMs`，同一目标时间的收敛轮次不会重复推进零时间移动。
- 遇到 `REGION_CONNECTION_REQUIRED` 时，门控器先让角色走到人员电梯站，创建载人请求；到站完成区域交接后，自动恢复原建筑目标。
- 修正副作用短路问题：移动释放不再写成会被 `changed ||= ...` 跳过的表达式。

### 验收

- 两张动态订单完成 12 个食谱步骤并由四台货梯送到地面交换站。
- 一名真实顾客从到店连续推进到点单、制作、上桌、消费、结账、离店、清桌和餐盘洗净；测试明确断言到达订单提交点前 `orderId` 仍为空。

## R9-05：采购、库存和财务收敛（已完成）

### 审计结论

- 正式桌面组合根只创建一个 `functionalFinance`，销售适配器、科技、建筑升级、船队、工资、招募、本地采购与自动补货全部注入该实例；各模块不存在私有余额。
- 正式采购到货只写入 `simulation.inventoryModule`；本地采购、航线采购与自动补货均不创建库存副本。
- 原有结构问题集中在应用协调层：`app-lifecycle` 与 `DesktopProcurementRuntime` 手工推进采购与船队，导致后台规则散落、业务 revision 与时钟推进混杂。

### 已实现

- 新增 `RestaurantProcurementProcess`，统一推进本地采购备货/出发/到货、远程船队返回/交接、等待批次分派以及管理员自动补货周期。
- 本地采购员与船长继续由统一 `RestaurantTaskCandidateProvider` 提供；进程只按职位、任务占用、车辆/飞艇容量及可用性筛选，不复制 Employment 或 Task 规则。
- 进程汇总备货完成、车辆到货、飞艇返航和下一次自动补货时间，并纳入统一 `nextTransitionUtcMs`。
- `RestaurantApplicationRuntime` 新增 `businessChanged`，纯时钟推进不再误报业务 revision；离散采购状态变化仍触发保存与读模型刷新。
- 桌面 ticker 已改由 `RestaurantApplicationRuntime.advanceTo()` 驱动采购进程；`DesktopProcurementRuntime` 删除候选人依赖与后台推进方法，只保留玩家命令和读模型。

### 验收证据

- 本地采购：同一 Finance 扣款，经采购员与小车自动执行后写入同一 Inventory。
- 航线采购：五件货物按飞艇容量拆成 3+2；第二批等待飞艇冷却后出发，返航、耐久、冷却和库存数量均按时间推进。
- 自动补货：剧情管理员在岗时遵守资金保留线创建采购；下一周期识别在途数量，不重复下单；离岗时返回 `MANAGER_UNAVAILABLE`。
- 正式组合根核对确认销售、采购、工资、招募、科技与建筑升级共享唯一 Finance，采购共享唯一 Inventory；各模块既有扣款、收入、工资和升级流水测试全部以该注入式状态为准。

### 第三刀第二块：17 个运营模块原子存档清单

- 新增 `RESTAURANT_OPERATIONAL_SAVE_MANIFEST`，统一登记应用运行时、库存、任务、订单、顾客、服务、餐盘、洗盘、食谱执行、移动、厨房设备、厨房产物、厨房步骤、托盘配送、物流需求、四台货梯和人员电梯的 module ID、schema version 与状态键。
- 导出时从各领域模块的唯一 `exportState()` 组装 17 个独立模块，不复制角色、财务、故事或其他既有状态；恢复时要求这组模块完整出现，禁止将一半新运营状态与一半旧经营状态拼接。
- 桌面 `GameSaveService` 继续兼容完全没有运营模块的旧 v2 存档；完整集合投影为 `restaurantOperational` 初始状态；集合残缺、版本错误或应用运行时损坏时只跳过运营恢复并追加明确诊断，不丢弃已通过校验的角色、财务、剧情与旧经营切片。
- 保存下一版状态时，所有已知运营 module ID 都进入受控替换/删除集合，残缺旧模块不会作为未知扩展被悄悄带回新存档。
- 恢复采取两阶段校验：存档边界先校验原子清单、schema 与状态头；生产组合根构造各领域模块时继续执行各模块的深层不变量校验，任一失败则安全初始化整组运营世界。
