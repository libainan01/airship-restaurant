# 飞艇餐厅 Godot 逐块重写技术方案 v0.1

> 决策状态：已确认。日期：2026-08-24。
>
> 本文描述新的目标技术路线与审核方式。现有 Electron、Phaser、React、TypeScript 版本保留为可运行参考，但不再作为新实现必须复刻的产品标准。

## 1. 为什么调整路线

当前实现已经证明大量业务规则可以运行，但实际制作暴露出两个根本问题：

1. 场景、美术、交互区域、站位和动画大量依赖代码坐标，无法在编辑器中直接观察和调整。
2. 管理界面依赖网页布局与 CSS，迭代结果网页感较强，整体风格和游戏场景难以在同一工具中预览。

同时，现有功能本身仍有需要重新判断的部分。因此本次不是把旧实现逐行翻译到新引擎，而是依据已确认需求，在 Godot 中按模块重新设计、实现和审核。

## 2. 核心决策

### 2.1 最终技术栈

- 引擎：Godot 4.7.2 .NET 稳定版；项目固定版本，升级引擎必须单独验证。
- 语言：生产代码统一使用 C#；Shader 仅负责视觉效果。除必要的编辑器工具外，不引入第二套生产脚本语言。
- 场景：Godot Scene、Node2D、Control、CanvasLayer、Area2D 与可编辑资源。
- UI：Godot Control、Container、Theme、StyleBox 和可复用 UI 场景，不再使用 React、HTML 或 CSS。
- 内容：JSON 或 Godot Resource 保存静态内容；是否继续使用 JSON 由对应内容模块审核时决定。
- 测试：纯 C# 领域层单元测试、Godot 场景测试和人工视觉验收三类并行。
- 发布目标：Windows 桌面伴宠优先；Web 不是本轮目标。

### 2.2 不采用长期混合运行时

最终产品不采用“Godot 画面＋Electron/Node 后台”的长期结构，也不在 Godot 中嵌入网页管理界面。迁移期允许旧应用和新应用并存运行，但二者不共享可写状态、不双写存档，也不在正式运行时互相依赖。

### 2.3 旧代码的定位

旧代码可以用于：

- 查询已经讨论过的业务边界；
- 复现复杂边界案例；
- 提取稳定内容 ID、测试数据和问题记录；
- 对比新旧交互体验。

旧代码不能用于：

- 强制新实现复刻用户不满意的行为；
- 直接复制高耦合协调器；
- 把 TypeScript 运行时作为新 Godot 客户端的永久后端；
- 未经重新确认就把旧测试结果视为新产品需求。

新模块的权威依据依次是：本轮审核结论、功能需求确认清单、对应模块设计卡、新实现测试。旧实现只排在其后。

## 3. 目标架构

~~~text
Godot Application
├─ Domain                 纯 C# 业务事实与规则，不依赖 Godot Node
├─ Application            命令、事务、时间推进、流程协调与读模型
├─ Content                角色、物品、食谱、建筑、科技和故事定义
├─ Persistence            新存档、版本迁移、备份与完整性校验
└─ Presentation
   ├─ World               2D 场景、角色、建筑、动画与特效
   ├─ Interaction         点击区、悬停、选择、拖拽与场景锚点
   └─ UI                  HUD、管理面板、弹层、提示和编辑模式
~~~

依赖方向固定为：

~~~text
Presentation → Application → Domain
Presentation → Content
Persistence  → Domain/Application 的公开存档契约
Domain       → 不依赖 Godot、UI、文件系统和系统时钟
~~~

业务完成仍由模拟时间和领域规则决定，不能依赖动画回调、窗口是否可见或玩家当前打开了哪个面板。

## 4. 可视场景与交互区域分离

每个可交互场景实例使用统一结构：

~~~text
BuildingOrCharacter
├─ VisualRoot
│  ├─ Sprite / Animation
│  ├─ Effects
│  └─ Lighting
├─ InteractionRoot
│  └─ 一个或多个 Area2D / CollisionShape2D / CollisionPolygon2D
├─ Anchors
│  ├─ WorkAnchor
│  ├─ ItemAnchor
│  ├─ DialogueAnchor
│  └─ StatusAnchor
└─ DebugRoot
~~~

约束如下：

1. VisualRoot 只决定画面，不直接处理业务命令。
2. InteractionRoot 可以是不规则、分离的多个区域；检测区不等于角色移动障碍。
3. Anchors 在编辑器中直接拖动，不在业务代码中写死场景像素坐标。
4. DebugRoot 可以显示点击区、锚点、实例 ID 和任务目标，发行版本默认隐藏。
5. 一个视觉对象可以有多个功能区域；多个区域也可以汇总为同一个业务入口。

## 5. UI 制作方式

UI 不再追求全部融入场景，也不恢复松散的网页式工具面板。结构分为：

- 场景内入口：建筑热点、角色热点、状态气泡和少量快捷动作；
- 常驻 HUD：时间、资金、关键通知、专注状态和右下角统一入口；
- 管理界面：仓库、食谱、采购、员工、科技树、花名册、账本与场景编辑；
- 临时层：详情、工具提示、确认框、剧情遮罩和编辑工具。

所有管理界面使用统一 Godot Theme 与可复用控件场景。布局在编辑器中预览，交互状态至少覆盖普通、悬停、按下、禁用、选中和键盘焦点。UI 的风格审核与功能审核同时进行，避免功能完成后再整体换皮。

## 6. 逐块重写与审核规则

每个模块都经过以下五步：

1. 需求卡：列出本块保留、删除、调整和待定规则。
2. 交互样板：先在 Godot 中提供可运行、可点击、可观察的最小版本。
3. 用户审核：由用户实际查看场景、操作路径和反馈表现。
4. 规则冻结：记录通过项和修改项，补齐自动测试与场景测试。
5. 进入下一块：只有用户明确通过后才开始下一个模块。

禁止以“旧版已经这样实现”为理由跳过审核。一个模块通过只代表该模块当前边界通过，不自动批准尚未展示的上下游规则。

每块交付至少包含：

- 可直接运行的 Godot 场景；
- 编辑器中的节点与资源位置说明；
- 一组正常路径和一组边界路径；
- 屏幕截图或短视觉记录；
- 对应自动测试结果；
- 本块已知限制和下一块接口；
- 不读取、不修改旧版玩家正式存档的声明。

## 7. 新重写阶段

### G0：Godot 可视化样板

只验证制作体验，不实现正式经营规则：

- 建立 Godot .NET 项目和目录边界；
- 重建一张飞艇与地面餐厅组合场景；
- 支持黎明、正午、傍晚三种光照预览；
- 放置一个不规则且不连续的建筑点击区；
- 制作右下角入口和一个仓库窗口样板；
- 提供点击区、锚点和层级 Debug 开关。

审核重点：场景是否方便调整、点击是否符合直觉、UI 是否还有网页感、修改效果是否能立即预览。

### G1：应用基础与新存档

- 稳定 ID、命令结果、领域事件和模拟时钟；
- 内容加载与校验；
- 新存档信封、测试存档和隔离目录；
- 暂停、专注模式与编辑模式的基础时间边界；
- 开发调试面板。

旧版正式存档不会被读取或改写。是否提供一次性导入器，在最终切换前单独决定。

### G2：场景、建筑与编辑模式

- 建筑实例、能力组件、占地尺寸和合法区域；
- 预览、预扣款、取消、确认、移动、换样式和实例升级；
- 编辑模式暂停；
- Visual、Interaction、Anchors 分离；
- 场景入口与管理入口指向同一功能。

### G3：角色、职位、日程、任务与移动

- 白夜城、奥托、顾客、员工和剧情角色统一对象；
- 员工标签、顾客标签、职位偏好和日程；
- 任务发布、资格、优先级、领取、中断和完成广播；
- 平面移动、工作锚点和人员电梯；
- 不自然站位与无意义移动专项审核。

### G4：库存、仓储、餐盘与交换物流

- 混合物品模型、预定、分类仓储和容量；
- 地面/飞艇交换站及存储目标；
- 四台单件小型货梯；
- 手动运输队列、阻塞与恢复；
- 橱柜、餐盘和洗盘循环。

### G5：顾客、点单与服务

- 来访、等候、入座、菜单、点单、订单和食材预定；
- 桌边点单与固定提交点；
- 上菜、结账、离店与清桌；
- 无订单取消的休闲节奏；
- 对话不强迫顾客离座或跨桌集合。

### G6：双层食谱与厨房

- 游戏用简化配料；
- 现实可制作的详细食谱；
- 并行和前置关系组成的步骤 DAG；
- 人员持续在场与自动烹煮；
- 设备工作位、厨师协作、装盘与菜品质量。

### G7：采购、舰队、财务与自动补货

- 本地采购员和采购小车；
- 航线、飞艇容量、飞艇冷却与船长；
- 自由采购和按食谱采购；
- 唯一资金流水、工资和日结；
- 剧情餐厅管理员提供自动补货。

### G8：成长、招募、剧情与专注

- 科技、建筑实例升级和载具升级重新归类；
- 招募、核心成员、技能、天赋和日程；
- 花名册、好感度、剧情时间窗和闲聊；
- 番茄钟、专注模式、收益和剧情延迟规则。

### G9：整合、桌面伴宠与正式切换

- Windows 透明桌面、窗口层级和性能策略；
- UI 输入优先级、键盘/鼠标与无障碍；
- 声音、通知、视觉反馈与设置；
- 长时间稳定性、存档恢复和打包；
- 决定旧存档导入策略；
- 用户完整验收后，才把 Godot 版本设为正式客户端。

## 8. 并行项目与删除策略

新 Godot 工程建立在独立目录中。G0—G8 期间：

- 不删除旧 Electron 应用；
- 不让旧应用写入新存档；
- 不让新应用读取玩家正式存档；
- 不为了保持两端一致而建立双写桥接；
- 旧应用只作为需求和体验对照。

只有 G9 完成并经用户确认后，才讨论归档 Electron、Phaser、React 代码。删除旧代码是单独的、可审计的任务，不夹在功能开发中执行。

## 9. 第一审核块

第一块固定为 G0，不先移植业务。

G0 展示内容必须足够让用户判断这条路线是否值得继续：

1. 能在 Godot 编辑器中直接移动飞艇、地面建筑和锚点；
2. 能直接编辑不连续点击区域并在运行时显示调试轮廓；
3. 能切换黎明、正午、傍晚并立即看到结果；
4. 能从场景热点或右下角入口打开同一个仓库样板；
5. 仓库样板不使用网页边框、浏览器默认控件或 CSS；
6. 修改场景不需要调整 C# 中的像素坐标。

G0 未经用户审核通过，不进入 G1。
