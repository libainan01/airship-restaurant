# 飞艇餐厅 R8 兼容清理阶段实现记录 v0.1

## R8-01：删除 M2Simulation 聚合状态（已完成）

### 审计结论

- 冻结护栏登记了 7 个 `M2Simulation` 直接依赖：桌面组合根、存档测试、实现本身以及运行时/稳定性/基线测试。
- 该对象内部直接组合 Inventory、Cooking、Logistics、Restaurant 与旧 Procurement，并承担统一时间推进；桌面同时接入了新的 Technology、LocalProcurement、AutomaticProcurement 等权威模块，因此旧升级和旧采购命令已经形成可删除的备用写路径。
- 当前存档仍以 `module.simulation` 保存这组连续经营状态。模块 ID 与 schemaVersion 在 R8-01 暂时保持，以免越过 R8-05 的历史存档迁移职责。

### 已完成切片

- `packages/core/src/m2-simulation.ts` 已迁移为 `gameplay-runtime.ts`，公开类型统一改为 `GameplayRuntime*`，实现类改为 `GameplayRuntime`；没有保留 `M2Simulation` 类型别名、转发导出或兼容文件。
- 桌面组合根、GameRuntime 端口、存档服务、基线生成器以及核心/桌面测试均已迁移到新类型。
- R0 冻结清单删除 `allowedM2SimulationTypeScriptFiles` 白名单；冻结脚本现在把任何 `M2Simulation` 符号或 `m2-simulation` 路径视为失败，当前直接依赖为 0。
- 新 GameplayRuntime、确定性稳定性、R0 基线、RuntimeState 与 GameSaveService 共 5 个测试文件、34 项测试通过；核心与桌面类型检查通过。

### 第二切片：关闭重复写入口

- `RuntimeSimulation` 与 `GameplayRuntime` 已移除旧 `purchaseUpgrade`、旧采购下单和旧自动采购配置 API；GameRuntime 不再回退写旧系统。桌面正式采购命令继续由 `DesktopProcurementRuntime` 截获并写入 `LocalProcurementModule` / `AutomaticProcurementModule`，科技和实例升级继续走各自正式模块。
- 旧 `ProcurementSystem.tryAutomaticOrder` 不再由 GameplayRuntime Tick 调用，因此旧档即使带有自动采购配置也不会继续生成第二套采购订单；历史在途状态仍可由原状态守卫读取并随时间到达，具体历史存档迁移留给 R8-05。
- 删除 4 项只验证废止升级/采购入口的旧聚合器测试；正式 Technology、实例升级、本地采购、远程采购和自动补货测试保持不变。全工作区类型检查通过，全量测试为 122 个 Vitest 文件、546 项测试与 4 项 Node 对白工具测试，全部通过。
- R0 固定命令结果保持兼容：无正式扩展时三条旧命令继续返回原拒绝码与消息，但不会产生任何业务写入；桌面组合根存在正式扩展时仍进入新模块。

### 第三切片：财务单一权威

- 新增 `RestaurantFinancePort` 与 `FinanceRestaurantRevenuePort`：餐点成交时直接调用 `FinanceModule.postIncome` 写入 `dish-sales` 账本；餐厅快照中的余额和累计支出只读取财务模块，不再维护第二份可写资金状态。
- 桌面组合根在创建 GameplayRuntime 前恢复 FinanceModule；没有正式财务状态的旧档仅在启动时读取一次 Restaurant 余额作为迁移初值。Technology、BuildingUpgrade、Fleet、Payroll、Recruitment、LocalProcurement 与 AutomaticProcurement 继续直接依赖同一个 FinanceModule。
- 删除 `LegacySimulationFinancePort`、余额检查点、强制支出镜像方法及其测试；Tick 不再每秒执行余额对账。冻结护栏禁止这些符号和旧文件路径重新进入源码。
- 新增餐厅收入直写账本的集成测试；完整 `npm run check` 通过（122 个 Vitest 文件、543 项测试与 4 项 Node 对白工具测试），桌面 `npm run smoke` 通过；冻结护栏显示财务镜像直接依赖为 0。

### 第四切片：拆除聚合存档载荷

- GameplayRuntime 只公开 `initialSlices` 与 `exportSaveSlices()`；删除聚合 `initialState` 和聚合 `exportState()`，运行时、8 小时稳定性测试与 R0 基线生成器全部改用分片恢复。
- 新存档分别写入 `module.gameplay-runtime`、`module.gameplay-inventory`、`module.cooking`、`module.logistics`、`module.restaurant` 与 `module.procurement-history`。旧 `module.simulation` 仅在 GameSaveService 的历史读取分支出现，下一次成功保存会移除旧模块且保留未知第三方模块。
- 聚合迁移类型明确改名为 `LegacyGameplayRuntimeState`，不再作为当前运行时状态；冻结护栏禁止正式应用重新写入 `module.simulation`、恢复聚合保存 API 或调用 `simulation.exportState()`。
- 5 组 R0 历史档、旧 v1 信封、旧 v2 模块、备份恢复、未知模块保留与全部现有可选模块通过迁移/往返测试。完整 `npm run check` 通过（122 个 Vitest 文件、543 项测试与 4 项 Node 测试），桌面烟雾测试通过；实际烟雾存档包含 6 个经营分片且不含 `module.simulation`。

### R8-01 退出结论

- `M2Simulation` 符号与路径为 0；旧升级、旧采购和财务镜像写入口为 0；GameplayRuntime 聚合保存写入为 0。
- 连续经营推进仍由 GameplayRuntime 编排，但资金和新增业务分别由正式领域模块持有唯一写入权，磁盘状态不再以一个 simulation 模块复制全部经营状态。

## R8-02：收紧 core 与 contracts 导出（已完成）

### 第一切片：旧实现退出公共根入口

- `@airship-restaurant/core` 根入口不再导出旧 `CookingSystem`、`InventorySystem`、`LogisticsSystem`、`ProcurementSystem` 与 `RestaurantSystem`；它们只供 GameplayRuntime 内部组合，核心单元测试改为内部源码导入，不再反向固化公共 API。
- 依赖边界门禁新增两条规则：跨包只能从 `@airship-restaurant/core` / `contracts` 根入口导入，禁止深入包内 `src`；core 根入口禁止重新公开上述 5 个旧经营实现。
- 删除无正式消费者的 `gameplay.purchase-upgrade` contracts 命令、验证器和 GameRuntime 拒绝分支。科技升级继续只使用 `technology.upgrade-node`，实例升级使用独立命令；仍由正式采购运行时使用的两条采购命令保留。
- 官方 R0 生成器改用分片 API 显式生成历史 v1 存档夹具并重建命令基线。contracts、R0 基线、历史存档和内部旧系统共 61 项聚焦测试通过，两项架构护栏通过。

### 第二切片：分层公开入口与循环依赖守卫

- `demo/index.ts` 只公开正式 `R6DemoApplication`，不再导出夹具和内部协调器；`runtime/index.ts` 不再公开 `RuntimeModuleRegistry`，相关测试改为直接引用内部实现。
- 新增 `projections/public.ts` 作为投影层正式入口，core 根入口不再通过内部投影桶文件泄漏 `ReadModelRegistry`。`R3ReadModelPublisher` 自行持有注册表，不再把内部装配对象作为构造参数暴露给消费者。
- 任务模块拆为纯桶入口、`task-module.ts` 实现和任务来源重建实现。新增运行时依赖图检查后首次运行即发现 `task/index.ts -> task-source-reconstruction.ts -> task/index.ts` 的真实循环，拆分后循环为 0。
- 架构门禁现在同时检查 renderer/core 隔离、core/contracts 跨包深层导入、旧经营实现根导出、demo/runtime 内部出口、投影正式入口以及 core 运行时循环依赖。

### R8-02 退出结论

- 旧经营实现、demo 夹具、RuntimeModuleRegistry 与 ReadModelRegistry 均不再从 `@airship-restaurant/core` 根入口意外公开；跨包消费者只能使用正式包入口。
- 废止 `gameplay.purchase-upgrade` 命令已从 contracts、运行时与基线夹具删除，正式科技和实例升级命令保持唯一入口。
- 完整 `npm run check` 通过：122 个 Vitest 文件、542 项测试、4 项 Node 脚本测试、全部工作区类型检查与生产构建通过；架构检查确认 core 运行时循环依赖为 0。

## R8-03：删除旧总快照依赖（已完成）

### 窗口协议切换为纯分片

- contracts 删除 `runtimeGetSnapshot`、`runtimeSnapshotChanged`、`RuntimeBridge.getSnapshot()`、`onSnapshotChanged()` 与 `SnapshotChangedListener`；preload 和 IpcRouter 同步删除总快照读取、广播、注册与注销逻辑。
- `CommandResult` 只保留命令接受/拒绝信息，不再携带 `GameSnapshot`。测试改为分别验证命令回执和权威 Runtime 状态，R0 命令结果夹具同步更新。
- Desktop 只订阅 `layout`、`inventory`、`characters`、`desktop-world`；Management 只订阅其 7 个业务切片。双窗口桥接烟雾验收改读 `desktop-world` 与 `operations`，R6 Demo 也通过 operations 切片轮询完成。
- IpcRouter 现在只依赖命令端口与 `RuntimeReadModelPort`，无权读取或订阅整份 Runtime 快照。

### 删除旧兼容门面

- 删除 `compatibility/` 目录、`LegacyGameRuntimeCompatibility` 与 `LegacyGameRuntimePort`；正式 `RuntimeReadModelFacade` 位于 `runtime/`，只公开命令路由与按 key 的读模型读取/订阅。
- 门面不再注册 `compatibility.game-snapshot`、提供 `getSnapshot()` 或全量订阅重载；聚合状态只在 core 内部作为 desktop-world / operations 投影输入。
- 架构门禁禁止 contracts 恢复总快照桥接，禁止 renderer/preload 引用 `GameSnapshot`，并禁止 core 恢复旧兼容门面符号或入口。

### R8-03 退出结论

- Desktop 与 Management 源码中的 `GameSnapshot`、总快照 IPC 和全量广播依赖均为 0；窗口恢复、更新和命令反馈全部走分片协议。
- 完整 `npm run check` 通过：122 个 Vitest 文件、542 项测试、4 项 Node 脚本测试、全部类型检查和生产构建通过。
- `npm run smoke` 通过：Desktop/Management 均以 ready 状态完成桥接，管理窗口的科技、采购、招募、成长、财务与 R6 Demo 验收正常。

## R8-04：删除 renderer 旧业务协调器（已完成）

### 审计与收口

- renderer 旧服务任务队列、奥托服务协调器、顾客事件协调器、顾客生命周期协调器和服务事件投影器此前已删除，冻结清单中的遗留业务写入保持为 0。
- 唯一登记的 `RestaurantNpcDirector` 实际是无状态只读投影，因此改名为 `RestaurantNpcProjector`，入口方法由 `update()` 改为 `project()`；它只把角色、顾客、对话与布局切片映射为 Actor Frame。
- `DesktopWorldRuntimeState` 改名为 `DesktopWorldPresentationModel`，明确其职责是缓存最新 desktop-world 切片、对话气泡、动画 revision 与提示文案，不创建任务、订单、顾客或剧情状态。
- Director 白名单清空。冻结护栏新增两项受保护 Projector/Model，禁止其导入命令、派发命令或调用任务生命周期写 API；未来新增 renderer `Coordinator`、`Queue` 或 `Director` 仍默认失败。

### R8-04 退出结论

- renderer 遗留业务写入 0，纯表现 Director 0；餐厅 NPC 与桌面世界均由只读切片驱动的 Projector、PresentationModel、Interpolator 和 Renderer 组成。
